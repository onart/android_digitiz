# 구현 계획

## 1차 마일스톤 (최소사양)

목표: **폰을 터치하면 PC에서 클릭되고, 슬라이드하면 드래그된다.**
게스트는 PC 절대 픽셀에 대응하는 그리드 + 핀치 조정 + 빈 사이드 메뉴.
호스트는 중계 + on/off + 콘솔 로거.

### 순서 원칙

ADB 전송으로 확정하면서 **프로젝트-킬러급 리스크는 사라졌다.**
남은 순서 원칙은 두 가지다.

1. **작업 10(입력 주입)을 단독 검증 가능하게 만든다.** 나중에 "클릭이 안 된다"가
   주입 문제인지 전송 문제인지 즉시 갈라진다.
2. **작업 3(폰에서 빈 앱 실행)과 작업 12(adb 기기 인식)를 Phase 0에서 확인한다.**
   기기·OEM별 드라이버 이슈(R3)는 있어도 조기에 드러나는 편이 낫다.

### Phase 4에서 걸린 것들

빌드 셋업이 구현보다 오래 걸렸다. 재발 방지를 위해 기록한다.

- `games-activity` 3.0.5는 **POM에 의존성을 선언하지 않는데** `GameActivity`는
  `AppCompatActivity`를 상속한다 → `androidx.appcompat` 직접 추가 + 테마도
  `Theme.AppCompat` 계열이어야 함
- 그 결과 kotlin-stdlib 중복 클래스 → jdk7/jdk8 아티팩트를 1.8 이상으로 제약
- JNI 심볼이 링커에 제거됨 → `--whole-archive` 필요
- `local.properties`에 백슬래시 금지 (Java Properties의 `\u` 이스케이프)
- **Android 15의 16KB 페이지**: 정렬 안 되면 시스템 경고 다이얼로그가 앱을 덮고
  포커스를 뺏는다 → `-DANDROID_SUPPORT_FLEXIBLE_PAGE_SIZES=ON`
- 메인 루프에서 poll 타임아웃을 루프 밖에서 한 번만 정하면, 포커스를 잃는 순간
  영원히 블록된다 (복귀 명령이 루프 안에서 오기 때문) → 매 반복 재계산

### Phase 4 검증 방법

실기에 손을 대지 않고도 전 구간을 확인할 수 있다.

```bash
adb exec-out screencap -p > screen.png     # 렌더링 확인
adb shell input swipe 150 550 500 800 500  # 스트로크 주입
```

720x1544 화면에서 1920x1080 데스크톱에 맞춘 상태(scale 0.33)로
`(150,550) → (500,800)` 을 그으면 호스트가 `DOWN (455, 148)` / `UP (1515, 906)` 을
받아야 한다. 계산값과 실측값이 일치하는지가 좌표계 전체의 검증이다.

| # | 작업 | 상태 |
|---|---|---|
| 23 | 종단 지연 측정 (클럭 오프셋 추정 + 롤링 통계 + UI 표시) | ✅ |

**측정 결과** (Galaxy S23 Ultra, HD+ 720x1544, USB 2.0)

| 구간 | 값 |
|---|---|
| PING/PONG 왕복 | 1.6 ~ 4.2 ms |
| 이벤트 → 호스트 도달 | 평균 11.3 ms, 최대 20.8 ms |
| `SendInput` 주입 | 측정 한계 이하 (수 µs) |

"이벤트 → 호스트"는 안드로이드가 터치에 찍은 타임스탬프 기준이므로
**터치스크린 스캔 지연은 포함되지 않는다.** 실제 손가락→커서는 이보다 높다.

두 클럭은 epoch가 다르므로 오프셋을 측정해야 한다. PONG 왕복 중 **가장 빠른**
것으로 추정한다 — 빠른 왕복은 대칭에 가깝지만 느린 왕복은 어느 쪽 다리에서
지연됐는지 알 수 없어 평균을 내면 오히려 틀어진다.

### Phase 5에서 드러난 것들

실기 생명주기 테스트가 아니었으면 못 잡았을 것들이다.

- **`GameActivityMotionEvent::eventTime` 은 나노초가 아니라 밀리초다.**
  기저 `AMotionEvent` API는 나노초라 헤더만 보면 틀리기 쉽다. 단위가 틀려도
  아무것도 실패하지 않고 지연 수치만 조용히 버려진다 → 런타임 정합성 검사를
  `TouchRouter::emit()` 에 상시 남겨뒀다
- **게스트에 수신 타임아웃이 없었다.** 호스트가 비정상 종료하면 adb가 터널을
  남기고, 소켓이 조용해질 뿐 닫히지 않는 경우가 있다 → 5초 무음이면 재연결
- **호스트가 꺼져 있을 때 재연결 루프가 시끄러웠다.** adb는 PC쪽에 아무도 없어도
  기기 쪽 연결을 받아주므로 `connect()` 는 성공하고 2초 뒤 끊긴다. 세션 성립
  판정을 시간이 아니라 **"호스트가 한 바이트라도 보냈는가"** 로 바꿨다
  (adb의 포기 지연이 하필 임계값 근처에 있어 시간 기준은 취약하다)
- **백그라운드 복귀 시 뷰가 초기화되던 문제.** 사용자가 맞춰둔 확대·이동이
  사라졌다 → 최초 1회와 데스크톱 구성 변경 시에만 다시 맞춘다
- **`tools/guest.sh` 가 호출자의 `MSYS_NO_PATHCONV` 를 상속받아** `adb install` 이
  조용히 실패했다. 설치되지도 않은 코드의 버그를 한참 쫓았다 → 스크립트가 해당
  변수를 `unset` 하고, 설치 후 **기기 APK의 md5를 빌드 산출물과 대조**한다

### 1차 이후 추가된 것

써보고 나서 필요하다고 판단되어 1차 범위 밖에서 추가한 항목들.

- **가로모드 고정** — PC 데스크톱이 가로라 세로 화면은 면적을 크게 낭비했다.
  1920x1080 기준 축척 0.33 → 0.59
- **180° 회전** (사이드 메뉴 헤더 버튼) — 매니페스트는 `sensorLandscape` 라
  들고 있을 때는 뒤집으면 따라오지만, 책상에 눕히면 가속도계가 수평인 폰의
  좌우를 구분하지 못해 처음 잡힌 방향이 그대로 굳는다. 이 앱이 쓰이는 자세가
  정확히 그 자세이고 USB 케이블이 나오는 쪽은 정해져 있으니, 손으로 반대를
  지정할 방법이 있어야 한다.
  **직접 그리지 않고 액티비티에 맡긴다** — `setRequestedOrientation()` 이면
  시스템 바, 카메라 홀, 터치 매핑이 전부 같이 넘어간다. 우리가 그리는 것만
  180° 돌리면 그 셋은 반대편에 남는다. 대신 누른 순간부터 방향이 고정되고
  (SharedPreferences에 저장, `onCreate` 에서 `super` 보다 먼저 적용해 실행 중
  회전이 보이지 않게 한다) 자동 회전은 끝난다 — 반쯤 돌려놓은 것을 센서가
  되돌릴 수 있으면 지정의 의미가 없다
- **입력 모드 토글** (사이드 메뉴) — Draw / Pan. Pan 모드는 한 손가락으로 뷰만
  움직이고 PC에는 아무것도 보내지 않는다. 현재 모드는 엣지 핸들에 표시되므로
  메뉴를 열지 않아도 "이 손가락이 PC에 그려지는가"를 알 수 있다
- **텍스트 렌더링** — 안드로이드 `Paint` → GL 텍스처. 설정이 둘을 넘어가면서
  그림만으로는 설명이 안 됐다. 폰트 번들 대신 플랫폼에 맡겨 한글을 공짜로 얻고,
  라벨은 `strings.xml` 에서 읽어 `values-ko` 가 그대로 적용된다
- **미니맵** — 확대해서 데스크톱 경계가 화면 밖으로 나갔을 때만 좌상단에 표시.
  **터치를 가로채지 않는다**: 그리는 면에 획을 삼키는 영역을 만드는 건
  조금 가려지는 것보다 나쁘다. 2차에서 화면 전송이 붙으면 숨긴다

### CR 스플라인 보정

도착한 샘플 사이를 Catmull-Rom 곡선으로 채운다. 솎아내기와 짝이다 — 한쪽이 점을
줄이고 한쪽이 곡선으로 메운다.

**1샘플 지연은 설계상 제거 불가능하다.** P1→P2 구간은 P0~P3로 정의되므로 P3가
와야 그릴 수 있다. 그리는 동안 커서가 한 입력 간격만큼 뒤따르고, 획을 놓을 때
따라잡는다. 그래서 옵션이고, UI에 실측 샘플 간격을 "추가 지연"으로 표시한다.

**Centripetal(α=0.5)** 을 쓴다. 우리 입력은 시간 또는 거리 중 하나로 솎이므로
간격이 불규칙한데, uniform 파라미터화는 불규칙한 간격에 첨점과 자기교차 고리로
답한다. UI에서 uniform/chordal도 고를 수 있지만 기본은 centripetal이다.

구현에서 주의한 것:

- 스트로크 시작에서 첫 점을 복제해 없는 P0을 대신한다. 끝에서도 마지막 점을
  복제해 경로가 손가락이 뗀 지점에 정확히 닿게 한다
- 같은 점이 연속으로 오면 knot 간격이 0이 되어 무게중심 좌표가 0으로 나눈다.
  그 구간은 직선으로 처리한다
- 세분 개수는 상한을 둔다. 한 번의 큰 점프가 수천 개의 `SendInput` 을 쏟아내면 안 된다
- 취소된 획은 남은 버퍼를 **버린다**. 흘려보내면 없던 선이 더 그려진다
- 꺼져 있을 때는 스무더를 통과시키지 않고 **우회**한다. 그래야 기존 경로와
  동일함이 증명된다 — 실제로 이걸 안 했다가 기존 테스트 5개가 깨졌고, UP에서
  여분의 이동이 주입되고 있었다

### 좌표 최소 간격

시간(0~40 ms)과 거리(0~16 dp)를 **각각** 설정하고, **둘 다 만족해야** 좌표를
보낸다. 느린 손놀림은 거리가 채워질 때까지, 빠른 손놀림은 시간이 찰 때까지
기다린다. 기본값은 둘 다 0 — 이 기능이 생기기 전과 같은 동작이다.

**이건 솎아내기(decimation)일 뿐 그 자체로 부드럽게 하지 않는다.** 고르게 벌어진
점을 호스트의 CR 스플라인에 먹이는 게 목적이므로 두 기능은 짝이다. 슬라이딩
모드에는 적용하지 않는다 — 포인팅이 끊겨 보이면 안 되기 때문이다.

값은 dp로 저장한다. 화면 밀도가 달라도 설정의 의미가 같아야 하기 때문이고,
라우터가 비교하는 건 원시 표면 픽셀이라 밀도를 알게 된 뒤에 변환한다.

실측 (400 ms에 500 px / 1.5 s에 54 px 스와이프):

| 설정 | 빠른 스와이프 | 느린 스와이프 |
|---|---|---|
| 0 / 0 | 26개 | 92개 |
| 20 ms / 0 | 14개 | — |
| 0 / 8 dp | — | 5개 |

두 축이 독립적으로 걸린다. 빠른 스와이프에서 거리 임계값이 안 걸리는 건 정상이다 —
이벤트당 이미 19 px씩 움직이므로 임계값을 넘는다.

슬라이더 때문에 사이드 메뉴에 **드래그 캡처**가 생겼다. 위젯이 hit test에서 true를
반환하면 그 손가락을 소유하고, 이후 move와 release가 그리로 간다. 2차의 커스텀
버튼 편집에도 필요한 기반이다.

### 슬라이딩 모드

지금의 Draw는 폰 표면과 PC 좌표가 1:1인 **절대** 매핑이다. 슬라이딩 모드는
축척만 남기고, 어디서 터치를 시작하든 **커서의 현재 위치에서** 그 움직임을
따라간다. 태블릿의 펜 모드 / 마우스 모드 구분과 같다.

절대는 그리기에 맞고, 상대는 일반적인 포인팅에 맞다 — 손가락을 떼고 다시 짚어도
커서가 튀지 않고, 작은 화면으로 넓은 데스크톱을 다 덮을 수 있다.

**커서 위치는 호스트가 소유한다.** 게스트는 커서가 어디 있는지 모르므로 와이어에는
델타가 흐른다. `Pointer` 의 `flags` 바이트가 비어 있으니 `bit0 = 상대 좌표` 로
정의하면 메시지도 파이프라인도 그대로 쓴다.

구현 시 놓치기 쉬운 것들:

- **매 `DOWN` 마다 `GetCursorPos()` 로 다시 읽어야 한다.** 스트로크 사이에 사용자가
  실제 마우스를 움직였을 수 있고, 내부 누산기만 믿으면 커서가 순간이동한다
- **누적은 부동소수로.** 축척 0.5배에서 1px 델타는 0.5px이고, 정수로 자르면 느린
  움직임이 아예 전달되지 않는다. 싸구려 트랙패드가 끈적한 이유가 이것이다
- **절대 기준 UI를 꺼야 한다.** 데스크톱 경계선과 미니맵은 상대 모드에서 아무것도
  의미하지 않으므로 그대로 두면 오해를 부른다. 화면 밖 입력 차단도 해당 없음
  (밖이라는 게 없다)
- **가장자리 클램프는 누산기까지.** 위치만 클램프하면 되돌아올 때 밀어낸 만큼
  헛돈다. 멀티모니터에서 어느 화면으로 넘어갈지도 규칙이 필요하다
- 핀치는 위치 조정에서 **감도 조정**으로 의미가 바뀌고, 두 손가락 이동은 의미를 잃는다
- 모드가 셋이 되면 지금의 "탭하면 뒤집기" 행은 순환이나 목록으로 바꿔야 한다
- 화면 전송(절대 영역)과 상대 모드는 충돌한다. 상대 모드에서는 전송을 끄거나
  커서를 따라다니게 해야 한다 **(← 화면 전송 구현 시 남은 과제)**

**구현 결과.** 누름 여부는 모드가 정한다: 그리기는 펜(닿으면 누름), 슬라이딩은
트랙패드(닿으면 이동만, 짧은 탭이 클릭). "누르지 않고 이동"은 추가 비용이 거의
없었다 — 호스트 파이프라인이 `Down` 없는 `Move` 를 이미 버튼 없는 커서 이동으로
처리하고 있었다. 새로 든 건 탭 판정뿐이다.

소수점은 **게스트가** 누적한다. 축척을 아는 쪽이 거기이고, 와이어에는 정수 델타만
흐르므로 호스트는 더하기만 하면 된다. 실측: 표면 (+500, +200) 스와이프가 축척
0.5867에서 정확히 (852, 340) px로 전달됐다 (이론값 852.2, 340.9).

가장자리는 **축 분리 클램프**다. 한 쌍으로 거부되면 x만, 그다음 y만 시도한다.
대각선으로 모서리에 부딪혀도 가장자리를 따라 미끄러지고, 멀티모니터의 계단진
경계에서도 별도 규칙 없이 동작한다.

### 활성 창 전달

호스트가 포커스를 가진 프로그램의 실행 파일 이름을 게스트에 보낸다
(`0x23 ACTIVE_WINDOW`). 게스트는 지금은 서랍 하단에 표시만 하고, 프리셋
자동 전환은 커스텀 버튼이 생기면 같은 값에 붙인다.

**커스텀 버튼 작업 때 이 표시를 서랍 밖으로 옮긴다.** 지금은 확인용이라
서랍에 있어도 되지만, 프리셋이 자동으로 바뀌기 시작하면 "지금 올라온 버튼이
왜 이것인가"의 답이 이 이름이다. 버튼과 같이 보이지 않으면 잘못된 프리셋이
올라와도 알 수가 없다. 서랍 하단 자리도 프리셋 관리 UI가 쓴다.

**`SetWinEventHook` 이 아니라 프레임당 폴링이다.** 훅이 몇 ms 빠르긴 한데
설치한 스레드가 메시지를 펌프하는 동안에만 살아 있고, 콜백에 사용자 데이터가
없어 파일 스코프 역참조 포인터가 필요하며, 일부 포커스 변경에서 조용하다.
`GetForegroundWindow()` 는 프레임당 포인터 비교 한 번이고 — 비싼 쪽인 이름
해석은 창이 실제로 바뀌었을 때만 돈다 — 놓칠 수가 없다.

**200 ms 정착 대기가 있다.** 알트탭은 거의 항상 셸을 거친다: 작업 표시줄이
실제로 0.1초쯤 포커스를 가져가므로, 그대로 흘리면 전환 한 번마다
`mspaint.exe → explorer.exe → msedge.exe` 가 나가고 프리셋이 기본값으로
떨어졌다 돌아온다. 로그로 확인하고 넣었다. 진짜로 탐색기를 쓰러 간 경우는
포커스가 거기 머무르므로 그대로 보고된다.

비교 기준은 **창이 아니라 (pid, 프로세스명)** 이다. 한 프로그램의 창 두 개를
오가는 건 프로그램이 바뀐 게 아니고, 프로그램에 걸린 프리셋이 들을 이유가 없다.

### 커스텀 버튼

**좌표**는 누르면 그 자리를 클릭하고, **단축키**는 `0x24 KEY` 를 보낸다.

좌표는 데스크톱이 아니라 **활성 창 기준 상대 좌표**다. "저장 아이콘"을 뜻하는
버튼은 창을 옮기거나 다른 모니터에서 열어도 계속 그걸 뜻해야 한다. 프로토콜
쪽 처리는 `WINDOW_RELATIVE` 항목 참조.

**모든 버튼은 누를 때가 아니라 뗄 때 동작한다.** 그래야 같은 누름이 나중에
길게 누르기(편집·삭제 메뉴)나 목록 스크롤로 밝혀질 여지가 남는다.

**영역 버튼은 물렸다.** PC 사각형의 축소판을 버튼에 넣어 그 안을 누르고
문지르는 방식이었는데, 종이 위에서는 말이 되지만 손에서는 우표만 한 것이
툴바를 대신하는 꼴이라 쓸 만하지 않았다. 편집기에서 더는 제공하지 않고
스트립 안의 드래그는 이제 스크롤이지만, 기기에 이미 저장된 버튼은 그대로
동작하고 종류 번호도 예약된 채 남는다 (`ButtonKind::Region`).

**텍스트 입력은 안드로이드 다이얼로그에 맡긴다.** GL 서피스에는 텍스트 필드가
없고, 타이핑이 필요한 순간은 추가와 편집 둘뿐이다. 다이얼로그를 쓰면 IME와
검증과 뒤로가기가 전부 딸려 오고, 네이티브 UI는 그리는 면으로 남는다. 결과는
JNI 콜백으로 네이티브에 돌아와 뮤텍스로 보호된 큐에 쌓이고, 렌더 스레드가
프레임마다 비운다.

가로 고정 앱이라 함정이 하나 더 있다. 세로가 아닌 화면에서 IME는 기본적으로
**전체화면 추출 편집기**로 뜨는데, 그러면 지금 입력하고 있는 그 다이얼로그를
통째로 가린다. `IME_FLAG_NO_EXTRACT_UI` 로 키보드를 아래에 붙여둔다.

여기에 함정이 하나 더 있었다: **다이얼로그가 뜨는 것 자체가 포커스 상실이라**,
길게 눌러 메뉴를 연 그 손가락은 ACTION_UP을 끝내 보내지 않는다. 위젯이 손가락을
잡은 채로 남아 다음 터치를 삼키므로, 포커스를 잃을 때 캡처를 명시적으로 끊는다.
영역 드래그 중이었다면 CANCEL을 **마지막으로 보낸 좌표로** 보낸다. 호스트는
메시지에 실린 좌표에서 버튼을 떼기 때문에, 기본값을 보내면 커서가 데스크톱
구석으로 날아가서 거기서 떨어진다.

저장은 `buttons.txt`, 한 줄에 버튼 하나, 탭 구분이다. JSON이 아닌 이유는 필드가
평평하고 고정이라 파서가 파일 전체보다 길어지고, 문제가 생겼을 때
`adb shell cat` 으로 그냥 읽히기 때문이다. 모든 변경은 즉시 기록된다 — 앱은
언제든 죽을 수 있고 나중에 저장할 순간은 없다. 이 부분은 안드로이드에 의존하지
않는 순수 C++ 이라 `guest/tests` 에서 데스크톱 툴체인으로 테스트한다.

### 버튼 스트립

한쪽 가장자리에 붙고 탭으로 접힌다. 스트립이 차지하는 픽셀은 그릴 수 없는
픽셀이라 접힘이 기본이다. 가로(아래 가장자리) / 세로(왼쪽 가장자리)는 서랍
헤더의 글리프 버튼으로 바꾸고, 방향과 접힘 상태는 `settings.txt` 에 남는다.

들어갈 자리보다 버튼이 많으면 **스트립 방향으로 끌어서 넘긴다.** 화살표만으로는
기능적으로 모자라다 — 모양이 요구하는 제스처가 드래그다. 화살표는 정확히 한 칸씩
움직이는 수단으로 남긴다.

끝에서 멈추지 않고 **순환**한다. 버튼이 열 몇 개인데 하드 스톱을 두면 왔던 길로
되돌아 끌라는 소리밖에 안 된다. 스크롤 위치는 인덱스가 아니라 **픽셀**이다:
드래그는 손가락이 간 만큼 움직여야지 버튼 단위로 튀면 안 된다. 손을 떼면 가장
가까운 칸 경계로 붙는다.

**길이는 사용자가 정한다.** 기본값은 해당 방향 길이의 절반에 들어가는 칸 수다 —
그리는 면 위의 오버레이가 아무도 시키지 않았는데 화면을 가로지르고 있으면 안 된다.
최소 1칸, 최대는 화면이 감당하는 만큼이고, 방향을 바꾸면 그쪽 최대로 잘린다.
이 기기(1544x720, 1.75배)에서는 가로 기본 3칸/최대 8칸, 세로 기본 1칸/최대 3칸이다.

가장자리에서 반쯤 들어온 칸은 `glScissor` 로 자른다. 잘라주지 않으면 스트립
바깥으로 삐져나와 화면을 가로지른다. `UiRenderer` 와 `TextRenderer` 양쪽에
클립이 필요한데, 도형과 글자가 서로 다른 패스이기 때문이다.

**드래그와 탭과 길게 누르기가 같은 누름에서 갈라진다.** 슬롭을 넘어 움직였고
그 움직임이 스트립 방향에 더 가까우면 스크롤, 가로지르는 쪽이면 그냥 취소,
안 움직이고 0.55초가 지나면 메뉴다.

세로 배치는 미니맵과 같은 구석을 쓴다. 미니맵이 그만큼 오른쪽에서 시작하게 했다.

활성 창 이름은 이제 서랍이 아니라 **스트립 옆에** 붙는다. 프리셋이 자동으로
바뀌기 시작하면 그 이름이 "지금 이 버튼들인 이유"의 답이고, 서랍을 열어야 읽히는
답은 그 역할을 못 한다.

### 프리셋

버튼 묶음에 이름을 주고, 원하면 프로그램 하나를 붙인다. 스트립의 탭을 길게
누르면 목록이 뜬다 — 전환, 새로 만들기, 이름 변경, 활성 창에 연결, 연결 해제,
삭제. 연결은 `ACTIVE_WINDOW` 가 보고하는 실행 파일 이름과 대조하며, 대소문자는
무시한다. 프로세스명 표기가 어떻게 오는지 보장된 게 없다.

**활성 창이 바뀌어도 자동으로 갈아끼우지 않는다.** 대신 스트립 옆에 `✓ ✕` 를
띄워서 물어본다. 원하는 창에 도달하기까지 포커스가 창 여섯 개를 스쳐 갈 수
있는데, 그때마다 스트립이 통째로 바뀌면 못 쓴다. 같은 이유로 **모달이 아니다**.
포커스가 옮겨가면 제안도 따라 바뀌거나 사라진다.

`✕` 는 그 프로그램에 대해 기억된다. 0.5초 뒤에 포커스가 돌아왔다고 다시 묻는
건 안 묻느니만 못하다. 다른 프로그램으로 옮겨가면 기억이 지워지므로, 나중에
돌아오면 다시 물어본다.

`✓` `✕` 글리프는 도형이 아니라 **글자로 그린다.** 여기 도형 어휘는 축에 정렬된
둥근 사각형뿐이라 대각선을 못 만든다. 실제로 처음엔 X 대신 +가 그려졌다.

저장 형식은 레코드 종류를 앞에 붙인 탭 구분이다: `P 이름 연결` 이 프리셋을
열고 `B ...` 가 그 안의 버튼이다. 숫자로 시작하는 줄은 프리셋이 생기기 전의
버튼으로 보고 첫 프리셋에 넣는다 — 기기에 이미 있던 버튼이 사라지면 안 된다.

**스트립은 버튼 목록이 아니라 스토어를 들고 있다.** 처음엔 현재 프리셋의 벡터를
가리키는 포인터를 잡아뒀는데, 두 가지로 틀렸다: 프리셋을 바꿔도 예전 버튼이
계속 보였고, 프리셋을 만들면 `presets_` 가 재할당되면서 그 포인터가 결국
매달린다. 스토어를 통해 읽으면 답이 낡을 수가 없다.

### 화면 전송 — 착수 전 조사

아직 구현 안 함. 조사만 해둔 것이라 착수할 때 다시 파지 않게 남긴다.

#### 코덱: libvpx가 아니라 H.264, 그런데 라이브러리가 아니라 플랫폼

둘 중 고르면 H.264인데, 코덱의 우열이 아니라 **하드웨어 비대칭** 때문이다.
VP9는 **인코딩 하드웨어가 사실상 없다** — 인텔 일부뿐이고 NVIDIA·AMD는 없다.
libvpx로 소프트웨어 인코딩하면 그 CPU는 포인터 주입과 경쟁한다. H.264는
데스크톱 GPU가 12년째 인코더를 달고 나오고(NVENC 2012, QSV 2011, VCE 2012),
안드로이드는 CDD가 초기부터 디코드를 요구해서 모든 SoC에 있다. 교집합이
사실상 100%다.

**다만 libx264도 openh264도 번들하지 않는다.** 플랫폼 인코더를 부르면
지연이 낮고, GPU 메모리에서 안 내려도 되고, **H.264 특허 부담이 OS·GPU 벤더
쪽에 남는다** (배포용으로 간주하기로 했으므로 이게 중요하다).

| | 추상화 | 비고 |
|---|---|---|
| Windows | Media Foundation MFT | `MFTEnumEx(MFT_ENUM_FLAG_HARDWARE)`. 벤더가 드라이버에 MFT를 넣어준다. 비동기 MFT라 이벤트 펌프가 필요하고, **`MFT_MESSAGE_SET_D3D_MANAGER` 로 D3D 디바이스를 물려야 GPU→CPU 리드백이 없다** |
| Linux | VA-API | 인텔 `iHD`, AMD Mesa. PipeWire의 DMA-BUF를 그대로 임포트 → 제로카피 |
| Linux + NVIDIA | **NVENC 직접** | `nvidia-vaapi-driver` 는 NVDEC 래퍼라 디코드 전용이다 |

NVENC를 직접 부르는 건 포터빌리티가 없다(벤더 SDK 세 개). 리눅스까지 가면
경로가 둘로 갈리므로 그때는 **FFmpeg 하나로 통일하는 게 코드가 제일 적다** —
`h264_mf` / `h264_vaapi` / `h264_nvenc` 가 이미 있다. 단 **`libx264` 를 켜면
GPL로 넘어간다.** 하드웨어 인코더만 켜서 동적 링크하면 LGPL이다.

캡처도 플랫폼마다 갈린다. X11은 `XShm` + **`XDamage`**(더티 사각형을 주므로
아래 타일 구조에 그대로 맞는다), Wayland는 직접 접근이 없어서
**PipeWire + `xdg-desktop-portal`** 를 거쳐야 하고 매 세션 사용자 동의가
필요하다(포털 4의 `restore_token` 으로 완화).

**게스트는 한 번만 쓰면 된다.** `AMediaCodec` 은 누가 인코딩했는지 모른다.
SPS/PPS를 `csd-0`/`csd-1` 로 주고 Annex-B NAL을 흘리면 끝이다.

#### 1단계는 더티 타일 + JPEG, 다만 여유가 빠듯하다

부족분이 약 10배인데 JPEG가 10~30배다. **여유가 아니라 상한이다.**
"1080p 전체를 1:1, 30fps"는 JPEG로 못 한다 — 그건 H.264가 필요한 설정이다.
실제로 쓰는 설정(영역 + 축소 + 15~30fps)은 넉넉하지만, 자명하지는 않다.

여유를 실제로 만드는 것, 레버리지 순: **영역**(1/4 면적 = 4배) →
**해상도 비율**(가로세로 절반 = 4배) → **프레임레이트**(참고용 화면에 30fps가
필요한가? 15fps면 2배) → 더티(평상시 큰 몫, 최악에 0) → **적응형**(송신 큐
깊이를 보고 품질·레이트를 알아서 낮춤).

설계가 해야 할 일은 한계에서 **입력이 망가지는 대신 화면 품질이 먼저
낮아지게** 만드는 것이다.

#### 함정들

**더티 타일은 상태가 있어서 프레임을 함부로 못 버린다.** H.264는 프레임을
버리면 화질이 잠깐 나빠지고 만다. 타일은 다르다 — N번 타일을 버리면 N+1번에는
그 변경이 없으니 **그 자리가 영구히 낡은 화면으로 남는다.** 그래서 버린
프레임의 더티 영역을 **다음 프레임에 합집합으로 이월**해야 하고, 어긋난 것을
낫게 할 **주기적 전체 갱신**이 보험으로 필요하다.

**TCP 헤드 오브 라인.** 우선순위 큐를 둬도 **커널 소켓에 넘긴 바이트는 이미
늦었다.** 200 KB 프레임을 한 번에 `send()` 하면 뒤따르는 POINTER는 200 KB
뒤다. 큐는 소켓 **위**에 있어야 하고 청크 사이에 입력을 확인해야 하며, 그러면
**청크 크기가 최악 입력 지연을 정한다** — 25 MB/s에서 16 KiB면 약 0.65 ms.
`PROTOCOL.md` 의 16 KiB 분할이 그래서 나온 숫자다.

**dirty가 안 도와주는 경우**: PC에서 동영상 재생(매 프레임 전면 변경),
스크롤과 캔버스 팬·줌. 스크롤은 DXGI가 **move rect** 를 따로 주므로 "이 영역을
저기로 옮겨라"만 보내고 새로 드러난 띠만 전송하면 된다 — 안 다루면 가장 흔한
동작이 최악 케이스가 된다. 그리고 아이러니하게도 **캔버스 자체가 사진 같은
내용**이라 JPEG가 제일 못하는 부분이다.

**JPEG도 공짜가 아니다.** CPU 인코딩이면 DXGI가 준 D3D11 텍스처를 내려야 하니
하드웨어 H.264가 피하는 그 리드백이 생긴다. libjpeg-turbo 1080p 단일 스레드가
대략 5~15 ms/frame이라 30fps면 코어 하나를 거의 다 쓰고, 그 CPU도 입력 경로와
경쟁한다. 타일은 MCU(16px) 경계에 정렬하고 품질을 고정해야 이음매가 안 보인다.
그리고 글자가 읽히게 품질을 올리는 만큼 대역폭 여유가 사라진다 — **품질 노브와
대역폭 노브는 같은 노브다.**

**링크 밖.** 폰은 충전되면서 계속 디코딩하므로 발열·스로틀링이 있고, 그건
**터치 지연에도 영향을 준다.** USB도 전용이 아니라 같은 루트 허브에 다른 장치가
붙으면 예산이 준다.

#### 코드 모양

이미 있는 플랫폼 인터페이스 패턴 그대로다.

```
IFrameSource   ← DxgiFrameSource / XDamageFrameSource / PipeWireFrameSource
IFrameEncoder  ← MfEncoder / VaapiEncoder      (또는 FFmpeg 하나로)
```

`IFrameSource` 가 "더티 사각형 + move 사각형 + GPU 핸들"을 내놓게 잡아두면
JPEG 단계와 H.264 단계가 같은 인터페이스를 쓴다. 1단계 작업이 버려지지 않는다.

### M2의 지배적 제약

USB 2.0 실효 대역폭은 **20~35 MB/s** 수준이다 (전송 계층과 무관하게 USB가 상한).
1080p BGRA 30fps = 250 MB/s로 **한 자릿수 배 초과**.
따라서 화면 전송은 압축이 선택이 아니라 필수이며, 해상도 비율 옵션이
사용자가 조절할 수 있는 유일한 완충 장치다.

흐름 제어에서 **입력 지연은 화면 지연보다 항상 우선한다.**
프레임이 큐를 막아 포인터 이벤트가 밀리면 디지타이저로서 실격이다.
