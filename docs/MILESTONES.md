# 구현 계획

## 1차 마일스톤 (최소사양)

목표: **폰을 터치하면 PC에서 클릭되고, 슬라이드하면 드래그된다.**
게스트는 PC 절대 픽셀에 대응하는 그리드 + 핀치 조정 + 빈 사이드 메뉴.
호스트는 중계 + on/off + 콘솔 로거.

### 순서 원칙

ADB 전송으로 확정하면서 **프로젝트-킬러급 리스크는 사라졌다.**
남은 순서 원칙은 두 가지다.

1. **작업 10(입력 주입)을 단독 검증 가능하게 만든다.** 나중에 "클릭이 안 된다"가
   주입 문제인지 전송 문제인지 즉시 갈라진다.
2. **작업 3(폰에서 빈 앱 실행)과 작업 12(adb 기기 인식)를 Phase 0에서 확인한다.**
   기기·OEM별 드라이버 이슈(R3)는 있어도 조기에 드러나는 편이 낫다.

### Phase 4에서 걸린 것들

빌드 셋업이 구현보다 오래 걸렸다. 재발 방지를 위해 기록한다.

- `games-activity` 3.0.5는 **POM에 의존성을 선언하지 않는데** `GameActivity`는
  `AppCompatActivity`를 상속한다 → `androidx.appcompat` 직접 추가 + 테마도
  `Theme.AppCompat` 계열이어야 함
- 그 결과 kotlin-stdlib 중복 클래스 → jdk7/jdk8 아티팩트를 1.8 이상으로 제약
- JNI 심볼이 링커에 제거됨 → `--whole-archive` 필요
- `local.properties`에 백슬래시 금지 (Java Properties의 `\u` 이스케이프)
- **Android 15의 16KB 페이지**: 정렬 안 되면 시스템 경고 다이얼로그가 앱을 덮고
  포커스를 뺏는다 → `-DANDROID_SUPPORT_FLEXIBLE_PAGE_SIZES=ON`
- 메인 루프에서 poll 타임아웃을 루프 밖에서 한 번만 정하면, 포커스를 잃는 순간
  영원히 블록된다 (복귀 명령이 루프 안에서 오기 때문) → 매 반복 재계산

### Phase 4 검증 방법

실기에 손을 대지 않고도 전 구간을 확인할 수 있다.

```bash
adb exec-out screencap -p > screen.png     # 렌더링 확인
adb shell input swipe 150 550 500 800 500  # 스트로크 주입
```

720x1544 화면에서 1920x1080 데스크톱에 맞춘 상태(scale 0.33)로
`(150,550) → (500,800)` 을 그으면 호스트가 `DOWN (455, 148)` / `UP (1515, 906)` 을
받아야 한다. 계산값과 실측값이 일치하는지가 좌표계 전체의 검증이다.

| # | 작업 | 상태 |
|---|---|---|
| 23 | 종단 지연 측정 (클럭 오프셋 추정 + 롤링 통계 + UI 표시) | ✅ |

**측정 결과** (Galaxy S23 Ultra, HD+ 720x1544, USB 2.0)

| 구간 | 값 |
|---|---|
| PING/PONG 왕복 | 1.6 ~ 4.2 ms |
| 이벤트 → 호스트 도달 | 평균 11.3 ms, 최대 20.8 ms |
| `SendInput` 주입 | 측정 한계 이하 (수 µs) |

"이벤트 → 호스트"는 안드로이드가 터치에 찍은 타임스탬프 기준이므로
**터치스크린 스캔 지연은 포함되지 않는다.** 실제 손가락→커서는 이보다 높다.

두 클럭은 epoch가 다르므로 오프셋을 측정해야 한다. PONG 왕복 중 **가장 빠른**
것으로 추정한다 — 빠른 왕복은 대칭에 가깝지만 느린 왕복은 어느 쪽 다리에서
지연됐는지 알 수 없어 평균을 내면 오히려 틀어진다.

### Phase 5에서 드러난 것들

실기 생명주기 테스트가 아니었으면 못 잡았을 것들이다.

- **`GameActivityMotionEvent::eventTime` 은 나노초가 아니라 밀리초다.**
  기저 `AMotionEvent` API는 나노초라 헤더만 보면 틀리기 쉽다. 단위가 틀려도
  아무것도 실패하지 않고 지연 수치만 조용히 버려진다 → 런타임 정합성 검사를
  `TouchRouter::emit()` 에 상시 남겨뒀다
- **게스트에 수신 타임아웃이 없었다.** 호스트가 비정상 종료하면 adb가 터널을
  남기고, 소켓이 조용해질 뿐 닫히지 않는 경우가 있다 → 5초 무음이면 재연결
- **호스트가 꺼져 있을 때 재연결 루프가 시끄러웠다.** adb는 PC쪽에 아무도 없어도
  기기 쪽 연결을 받아주므로 `connect()` 는 성공하고 2초 뒤 끊긴다. 세션 성립
  판정을 시간이 아니라 **"호스트가 한 바이트라도 보냈는가"** 로 바꿨다
  (adb의 포기 지연이 하필 임계값 근처에 있어 시간 기준은 취약하다)
- **백그라운드 복귀 시 뷰가 초기화되던 문제.** 사용자가 맞춰둔 확대·이동이
  사라졌다 → 최초 1회와 데스크톱 구성 변경 시에만 다시 맞춘다
- **`tools/guest.sh` 가 호출자의 `MSYS_NO_PATHCONV` 를 상속받아** `adb install` 이
  조용히 실패했다. 설치되지도 않은 코드의 버그를 한참 쫓았다 → 스크립트가 해당
  변수를 `unset` 하고, 설치 후 **기기 APK의 md5를 빌드 산출물과 대조**한다

### 1차 이후 추가된 것

써보고 나서 필요하다고 판단되어 1차 범위 밖에서 추가한 항목들.

- **가로모드 고정** — PC 데스크톱이 가로라 세로 화면은 면적을 크게 낭비했다.
  1920x1080 기준 축척 0.33 → 0.59
- **180° 회전** (사이드 메뉴 헤더 버튼) — 매니페스트는 `sensorLandscape` 라
  들고 있을 때는 뒤집으면 따라오지만, 책상에 눕히면 가속도계가 수평인 폰의
  좌우를 구분하지 못해 처음 잡힌 방향이 그대로 굳는다. 이 앱이 쓰이는 자세가
  정확히 그 자세이고 USB 케이블이 나오는 쪽은 정해져 있으니, 손으로 반대를
  지정할 방법이 있어야 한다.
  **직접 그리지 않고 액티비티에 맡긴다** — `setRequestedOrientation()` 이면
  시스템 바, 카메라 홀, 터치 매핑이 전부 같이 넘어간다. 우리가 그리는 것만
  180° 돌리면 그 셋은 반대편에 남는다. 대신 누른 순간부터 방향이 고정되고
  (SharedPreferences에 저장, `onCreate` 에서 `super` 보다 먼저 적용해 실행 중
  회전이 보이지 않게 한다) 자동 회전은 끝난다 — 반쯤 돌려놓은 것을 센서가
  되돌릴 수 있으면 지정의 의미가 없다
- **입력 모드 토글** (사이드 메뉴) — Draw / Pan. Pan 모드는 한 손가락으로 뷰만
  움직이고 PC에는 아무것도 보내지 않는다. 현재 모드는 엣지 핸들에 표시되므로
  메뉴를 열지 않아도 "이 손가락이 PC에 그려지는가"를 알 수 있다
- **텍스트 렌더링** — 안드로이드 `Paint` → GL 텍스처. 설정이 둘을 넘어가면서
  그림만으로는 설명이 안 됐다. 폰트 번들 대신 플랫폼에 맡겨 한글을 공짜로 얻고,
  라벨은 `strings.xml` 에서 읽어 `values-ko` 가 그대로 적용된다
- **미니맵** — 확대해서 데스크톱 경계가 화면 밖으로 나갔을 때만 좌상단에 표시.
  **터치를 가로채지 않는다**: 그리는 면에 획을 삼키는 영역을 만드는 건
  조금 가려지는 것보다 나쁘다. 2차에서 화면 전송이 붙으면 숨긴다

### CR 스플라인 보정

도착한 샘플 사이를 Catmull-Rom 곡선으로 채운다. 솎아내기와 짝이다 — 한쪽이 점을
줄이고 한쪽이 곡선으로 메운다.

**1샘플 지연은 설계상 제거 불가능하다.** P1→P2 구간은 P0~P3로 정의되므로 P3가
와야 그릴 수 있다. 그리는 동안 커서가 한 입력 간격만큼 뒤따르고, 획을 놓을 때
따라잡는다. 그래서 옵션이고, UI에 실측 샘플 간격을 "추가 지연"으로 표시한다.

**Centripetal(α=0.5)** 을 쓴다. 우리 입력은 시간 또는 거리 중 하나로 솎이므로
간격이 불규칙한데, uniform 파라미터화는 불규칙한 간격에 첨점과 자기교차 고리로
답한다. UI에서 uniform/chordal도 고를 수 있지만 기본은 centripetal이다.

구현에서 주의한 것:

- 스트로크 시작에서 첫 점을 복제해 없는 P0을 대신한다. 끝에서도 마지막 점을
  복제해 경로가 손가락이 뗀 지점에 정확히 닿게 한다
- 같은 점이 연속으로 오면 knot 간격이 0이 되어 무게중심 좌표가 0으로 나눈다.
  그 구간은 직선으로 처리한다
- 세분 개수는 상한을 둔다. 한 번의 큰 점프가 수천 개의 `SendInput` 을 쏟아내면 안 된다
- 취소된 획은 남은 버퍼를 **버린다**. 흘려보내면 없던 선이 더 그려진다
- 꺼져 있을 때는 스무더를 통과시키지 않고 **우회**한다. 그래야 기존 경로와
  동일함이 증명된다 — 실제로 이걸 안 했다가 기존 테스트 5개가 깨졌고, UP에서
  여분의 이동이 주입되고 있었다

### 좌표 최소 간격

시간(0~40 ms)과 거리(0~16 dp)를 **각각** 설정하고, **둘 다 만족해야** 좌표를
보낸다. 느린 손놀림은 거리가 채워질 때까지, 빠른 손놀림은 시간이 찰 때까지
기다린다. 기본값은 둘 다 0 — 이 기능이 생기기 전과 같은 동작이다.

**이건 솎아내기(decimation)일 뿐 그 자체로 부드럽게 하지 않는다.** 고르게 벌어진
점을 호스트의 CR 스플라인에 먹이는 게 목적이므로 두 기능은 짝이다. 슬라이딩
모드에는 적용하지 않는다 — 포인팅이 끊겨 보이면 안 되기 때문이다.

값은 dp로 저장한다. 화면 밀도가 달라도 설정의 의미가 같아야 하기 때문이고,
라우터가 비교하는 건 원시 표면 픽셀이라 밀도를 알게 된 뒤에 변환한다.

실측 (400 ms에 500 px / 1.5 s에 54 px 스와이프):

| 설정 | 빠른 스와이프 | 느린 스와이프 |
|---|---|---|
| 0 / 0 | 26개 | 92개 |
| 20 ms / 0 | 14개 | — |
| 0 / 8 dp | — | 5개 |

두 축이 독립적으로 걸린다. 빠른 스와이프에서 거리 임계값이 안 걸리는 건 정상이다 —
이벤트당 이미 19 px씩 움직이므로 임계값을 넘는다.

슬라이더 때문에 사이드 메뉴에 **드래그 캡처**가 생겼다. 위젯이 hit test에서 true를
반환하면 그 손가락을 소유하고, 이후 move와 release가 그리로 간다. 2차의 커스텀
버튼 편집에도 필요한 기반이다.

### 슬라이딩 모드

지금의 Draw는 폰 표면과 PC 좌표가 1:1인 **절대** 매핑이다. 슬라이딩 모드는
축척만 남기고, 어디서 터치를 시작하든 **커서의 현재 위치에서** 그 움직임을
따라간다. 태블릿의 펜 모드 / 마우스 모드 구분과 같다.

절대는 그리기에 맞고, 상대는 일반적인 포인팅에 맞다 — 손가락을 떼고 다시 짚어도
커서가 튀지 않고, 작은 화면으로 넓은 데스크톱을 다 덮을 수 있다.

**커서 위치는 호스트가 소유한다.** 게스트는 커서가 어디 있는지 모르므로 와이어에는
델타가 흐른다. `Pointer` 의 `flags` 바이트가 비어 있으니 `bit0 = 상대 좌표` 로
정의하면 메시지도 파이프라인도 그대로 쓴다.

구현 시 놓치기 쉬운 것들:

- **매 `DOWN` 마다 `GetCursorPos()` 로 다시 읽어야 한다.** 스트로크 사이에 사용자가
  실제 마우스를 움직였을 수 있고, 내부 누산기만 믿으면 커서가 순간이동한다
- **누적은 부동소수로.** 축척 0.5배에서 1px 델타는 0.5px이고, 정수로 자르면 느린
  움직임이 아예 전달되지 않는다. 싸구려 트랙패드가 끈적한 이유가 이것이다
- **절대 기준 UI를 꺼야 한다.** 데스크톱 경계선과 미니맵은 상대 모드에서 아무것도
  의미하지 않으므로 그대로 두면 오해를 부른다. 화면 밖 입력 차단도 해당 없음
  (밖이라는 게 없다)
- **가장자리 클램프는 누산기까지.** 위치만 클램프하면 되돌아올 때 밀어낸 만큼
  헛돈다. 멀티모니터에서 어느 화면으로 넘어갈지도 규칙이 필요하다
- 핀치는 위치 조정에서 **감도 조정**으로 의미가 바뀌고, 두 손가락 이동은 의미를 잃는다
- 모드가 셋이 되면 지금의 "탭하면 뒤집기" 행은 순환이나 목록으로 바꿔야 한다
- 화면 전송(절대 영역)과 상대 모드는 충돌한다. 상대 모드에서는 전송을 끄거나
  커서를 따라다니게 해야 한다. **지금은 끈다** — 미니맵과 화면 윤곽을 끄는 것과
  같은 이유다. 더 나은 답은 아직 없다

**구현 결과.** 누름 여부는 모드가 정한다: 그리기는 펜(닿으면 누름), 슬라이딩은
트랙패드(닿으면 이동만, 짧은 탭이 클릭). "누르지 않고 이동"은 추가 비용이 거의
없었다 — 호스트 파이프라인이 `Down` 없는 `Move` 를 이미 버튼 없는 커서 이동으로
처리하고 있었다. 새로 든 건 탭 판정뿐이다.

소수점은 **게스트가** 누적한다. 축척을 아는 쪽이 거기이고, 와이어에는 정수 델타만
흐르므로 호스트는 더하기만 하면 된다. 실측: 표면 (+500, +200) 스와이프가 축척
0.5867에서 정확히 (852, 340) px로 전달됐다 (이론값 852.2, 340.9).

가장자리는 **축 분리 클램프**다. 한 쌍으로 거부되면 x만, 그다음 y만 시도한다.
대각선으로 모서리에 부딪혀도 가장자리를 따라 미끄러지고, 멀티모니터의 계단진
경계에서도 별도 규칙 없이 동작한다.

### 활성 창 전달

호스트가 포커스를 가진 프로그램의 실행 파일 이름을 게스트에 보낸다
(`0x23 ACTIVE_WINDOW`). 게스트는 지금은 서랍 하단에 표시만 하고, 프리셋
자동 전환은 커스텀 버튼이 생기면 같은 값에 붙인다.

**커스텀 버튼 작업 때 이 표시를 서랍 밖으로 옮긴다.** 지금은 확인용이라
서랍에 있어도 되지만, 프리셋이 자동으로 바뀌기 시작하면 "지금 올라온 버튼이
왜 이것인가"의 답이 이 이름이다. 버튼과 같이 보이지 않으면 잘못된 프리셋이
올라와도 알 수가 없다. 서랍 하단 자리도 프리셋 관리 UI가 쓴다.

**`SetWinEventHook` 이 아니라 프레임당 폴링이다.** 훅이 몇 ms 빠르긴 한데
설치한 스레드가 메시지를 펌프하는 동안에만 살아 있고, 콜백에 사용자 데이터가
없어 파일 스코프 역참조 포인터가 필요하며, 일부 포커스 변경에서 조용하다.
`GetForegroundWindow()` 는 프레임당 포인터 비교 한 번이고 — 비싼 쪽인 이름
해석은 창이 실제로 바뀌었을 때만 돈다 — 놓칠 수가 없다.

**200 ms 정착 대기가 있다.** 알트탭은 거의 항상 셸을 거친다: 작업 표시줄이
실제로 0.1초쯤 포커스를 가져가므로, 그대로 흘리면 전환 한 번마다
`mspaint.exe → explorer.exe → msedge.exe` 가 나가고 프리셋이 기본값으로
떨어졌다 돌아온다. 로그로 확인하고 넣었다. 진짜로 탐색기를 쓰러 간 경우는
포커스가 거기 머무르므로 그대로 보고된다.

비교 기준은 **창이 아니라 (pid, 프로세스명)** 이다. 한 프로그램의 창 두 개를
오가는 건 프로그램이 바뀐 게 아니고, 프로그램에 걸린 프리셋이 들을 이유가 없다.

### 커스텀 버튼

**좌표**는 누르면 그 자리를 클릭하고, **단축키**는 `0x24 KEY` 를 보낸다.

좌표는 데스크톱이 아니라 **활성 창 기준 상대 좌표**다. "저장 아이콘"을 뜻하는
버튼은 창을 옮기거나 다른 모니터에서 열어도 계속 그걸 뜻해야 한다. 프로토콜
쪽 처리는 `WINDOW_RELATIVE` 항목 참조.

**모든 버튼은 누를 때가 아니라 뗄 때 동작한다.** 그래야 같은 누름이 나중에
길게 누르기(편집·삭제 메뉴)나 목록 스크롤로 밝혀질 여지가 남는다.

**영역 버튼은 물렸다.** PC 사각형의 축소판을 버튼에 넣어 그 안을 누르고
문지르는 방식이었는데, 종이 위에서는 말이 되지만 손에서는 우표만 한 것이
툴바를 대신하는 꼴이라 쓸 만하지 않았다. 편집기에서 더는 제공하지 않고
스트립 안의 드래그는 이제 스크롤이지만, 기기에 이미 저장된 버튼은 그대로
동작하고 종류 번호도 예약된 채 남는다 (`ButtonKind::Region`).

**텍스트 입력은 안드로이드 다이얼로그에 맡긴다.** GL 서피스에는 텍스트 필드가
없고, 타이핑이 필요한 순간은 추가와 편집 둘뿐이다. 다이얼로그를 쓰면 IME와
검증과 뒤로가기가 전부 딸려 오고, 네이티브 UI는 그리는 면으로 남는다. 결과는
JNI 콜백으로 네이티브에 돌아와 뮤텍스로 보호된 큐에 쌓이고, 렌더 스레드가
프레임마다 비운다.

가로 고정 앱이라 함정이 하나 더 있다. 세로가 아닌 화면에서 IME는 기본적으로
**전체화면 추출 편집기**로 뜨는데, 그러면 지금 입력하고 있는 그 다이얼로그를
통째로 가린다. `IME_FLAG_NO_EXTRACT_UI` 로 키보드를 아래에 붙여둔다.

여기에 함정이 하나 더 있었다: **다이얼로그가 뜨는 것 자체가 포커스 상실이라**,
길게 눌러 메뉴를 연 그 손가락은 ACTION_UP을 끝내 보내지 않는다. 위젯이 손가락을
잡은 채로 남아 다음 터치를 삼키므로, 포커스를 잃을 때 캡처를 명시적으로 끊는다.
영역 드래그 중이었다면 CANCEL을 **마지막으로 보낸 좌표로** 보낸다. 호스트는
메시지에 실린 좌표에서 버튼을 떼기 때문에, 기본값을 보내면 커서가 데스크톱
구석으로 날아가서 거기서 떨어진다.

저장은 `buttons.txt`, 한 줄에 버튼 하나, 탭 구분이다. JSON이 아닌 이유는 필드가
평평하고 고정이라 파서가 파일 전체보다 길어지고, 문제가 생겼을 때
`adb shell cat` 으로 그냥 읽히기 때문이다. 모든 변경은 즉시 기록된다 — 앱은
언제든 죽을 수 있고 나중에 저장할 순간은 없다. 이 부분은 안드로이드에 의존하지
않는 순수 C++ 이라 `guest/tests` 에서 데스크톱 툴체인으로 테스트한다.

### 버튼 스트립

한쪽 가장자리에 붙고 탭으로 접힌다. 스트립이 차지하는 픽셀은 그릴 수 없는
픽셀이라 접힘이 기본이다. 가로(아래 가장자리) / 세로(왼쪽 가장자리)는 서랍
헤더의 글리프 버튼으로 바꾸고, 방향과 접힘 상태는 `settings.txt` 에 남는다.

들어갈 자리보다 버튼이 많으면 **스트립 방향으로 끌어서 넘긴다.** 화살표만으로는
기능적으로 모자라다 — 모양이 요구하는 제스처가 드래그다. 화살표는 정확히 한 칸씩
움직이는 수단으로 남긴다.

끝에서 멈추지 않고 **순환**한다. 버튼이 열 몇 개인데 하드 스톱을 두면 왔던 길로
되돌아 끌라는 소리밖에 안 된다. 스크롤 위치는 인덱스가 아니라 **픽셀**이다:
드래그는 손가락이 간 만큼 움직여야지 버튼 단위로 튀면 안 된다. 손을 떼면 가장
가까운 칸 경계로 붙는다.

**길이는 사용자가 정한다.** 기본값은 해당 방향 길이의 절반에 들어가는 칸 수다 —
그리는 면 위의 오버레이가 아무도 시키지 않았는데 화면을 가로지르고 있으면 안 된다.
최소 1칸, 최대는 화면이 감당하는 만큼이고, 방향을 바꾸면 그쪽 최대로 잘린다.
이 기기(1544x720, 1.75배)에서는 가로 기본 3칸/최대 8칸, 세로 기본 1칸/최대 3칸이다.

가장자리에서 반쯤 들어온 칸은 `glScissor` 로 자른다. 잘라주지 않으면 스트립
바깥으로 삐져나와 화면을 가로지른다. `UiRenderer` 와 `TextRenderer` 양쪽에
클립이 필요한데, 도형과 글자가 서로 다른 패스이기 때문이다.

**드래그와 탭과 길게 누르기가 같은 누름에서 갈라진다.** 슬롭을 넘어 움직였고
그 움직임이 스트립 방향에 더 가까우면 스크롤, 가로지르는 쪽이면 그냥 취소,
안 움직이고 0.55초가 지나면 메뉴다.

세로 배치는 미니맵과 같은 구석을 쓴다. 미니맵이 그만큼 오른쪽에서 시작하게 했다.

활성 창 이름은 이제 서랍이 아니라 **스트립 옆에** 붙는다. 프리셋이 자동으로
바뀌기 시작하면 그 이름이 "지금 이 버튼들인 이유"의 답이고, 서랍을 열어야 읽히는
답은 그 역할을 못 한다.

### 프리셋

버튼 묶음에 이름을 주고, 원하면 프로그램 하나를 붙인다. 스트립의 탭을 길게
누르면 목록이 뜬다 — 전환, 새로 만들기, 이름 변경, 활성 창에 연결, 연결 해제,
삭제. 연결은 `ACTIVE_WINDOW` 가 보고하는 실행 파일 이름과 대조하며, 대소문자는
무시한다. 프로세스명 표기가 어떻게 오는지 보장된 게 없다.

**활성 창이 바뀌어도 자동으로 갈아끼우지 않는다.** 대신 스트립 옆에 `✓ ✕` 를
띄워서 물어본다. 원하는 창에 도달하기까지 포커스가 창 여섯 개를 스쳐 갈 수
있는데, 그때마다 스트립이 통째로 바뀌면 못 쓴다. 같은 이유로 **모달이 아니다**.
포커스가 옮겨가면 제안도 따라 바뀌거나 사라진다.

`✕` 는 그 프로그램에 대해 기억된다. 0.5초 뒤에 포커스가 돌아왔다고 다시 묻는
건 안 묻느니만 못하다. 다른 프로그램으로 옮겨가면 기억이 지워지므로, 나중에
돌아오면 다시 물어본다.

`✓` `✕` 글리프는 도형이 아니라 **글자로 그린다.** 여기 도형 어휘는 축에 정렬된
둥근 사각형뿐이라 대각선을 못 만든다. 실제로 처음엔 X 대신 +가 그려졌다.

저장 형식은 레코드 종류를 앞에 붙인 탭 구분이다: `P 이름 연결` 이 프리셋을
열고 `B ...` 가 그 안의 버튼이다. 숫자로 시작하는 줄은 프리셋이 생기기 전의
버튼으로 보고 첫 프리셋에 넣는다 — 기기에 이미 있던 버튼이 사라지면 안 된다.

**스트립은 버튼 목록이 아니라 스토어를 들고 있다.** 처음엔 현재 프리셋의 벡터를
가리키는 포인터를 잡아뒀는데, 두 가지로 틀렸다: 프리셋을 바꿔도 예전 버튼이
계속 보였고, 프리셋을 만들면 `presets_` 가 재할당되면서 그 포인터가 결국
매달린다. 스토어를 통해 읽으면 답이 낡을 수가 없다.

### 화면 전송 — 착수 전 조사

아직 구현 안 함. 조사만 해둔 것이라 착수할 때 다시 파지 않게 남긴다.

#### 코덱: libvpx가 아니라 H.264, 그런데 라이브러리가 아니라 플랫폼

둘 중 고르면 H.264인데, 코덱의 우열이 아니라 **하드웨어 비대칭** 때문이다.
VP9는 **인코딩 하드웨어가 사실상 없다** — 인텔 일부뿐이고 NVIDIA·AMD는 없다.
libvpx로 소프트웨어 인코딩하면 그 CPU는 포인터 주입과 경쟁한다. H.264는
데스크톱 GPU가 12년째 인코더를 달고 나오고(NVENC 2012, QSV 2011, VCE 2012),
안드로이드는 CDD가 초기부터 디코드를 요구해서 모든 SoC에 있다. 교집합이
사실상 100%다.

**다만 libx264도 openh264도 번들하지 않는다.** 플랫폼 인코더를 부르면
지연이 낮고, GPU 메모리에서 안 내려도 되고, **H.264 특허 부담이 OS·GPU 벤더
쪽에 남는다** (배포용으로 간주하기로 했으므로 이게 중요하다).

| | 추상화 | 비고 |
|---|---|---|
| Windows | Media Foundation MFT | `MFTEnumEx(MFT_ENUM_FLAG_HARDWARE)`. 벤더가 드라이버에 MFT를 넣어준다. 비동기 MFT라 이벤트 펌프가 필요하고, **`MFT_MESSAGE_SET_D3D_MANAGER` 로 D3D 디바이스를 물려야 GPU→CPU 리드백이 없다** |
| Linux | VA-API | 인텔 `iHD`, AMD Mesa. PipeWire의 DMA-BUF를 그대로 임포트 → 제로카피 |
| Linux + NVIDIA | **NVENC 직접** | `nvidia-vaapi-driver` 는 NVDEC 래퍼라 디코드 전용이다 |

NVENC를 직접 부르는 건 포터빌리티가 없다(벤더 SDK 세 개). 리눅스까지 가면
경로가 둘로 갈리므로 그때는 **FFmpeg 하나로 통일하는 게 코드가 제일 적다** —
`h264_mf` / `h264_vaapi` / `h264_nvenc` 가 이미 있다. 단 **`libx264` 를 켜면
GPL로 넘어간다.** 하드웨어 인코더만 켜서 동적 링크하면 LGPL이다.

캡처도 플랫폼마다 갈린다. X11은 `XShm` + **`XDamage`**(더티 사각형을 주므로
아래 타일 구조에 그대로 맞는다), Wayland는 직접 접근이 없어서
**PipeWire + `xdg-desktop-portal`** 를 거쳐야 하고 매 세션 사용자 동의가
필요하다(포털 4의 `restore_token` 으로 완화).

**게스트는 한 번만 쓰면 된다.** `AMediaCodec` 은 누가 인코딩했는지 모른다.
SPS/PPS를 `csd-0`/`csd-1` 로 주고 Annex-B NAL을 흘리면 끝이다.

#### 1단계: 더티 타일 라운드로빈 + ETC2 + zstd

처음엔 JPEG를 생각했는데, 부족분이 약 10배인데 JPEG가 10~30배라 **여유가
아니라 상한이었다.** 스케줄링과 포맷을 같이 바꾸면 훨씬 낫다.

**고정 크기(절대크기) 타일을 더티 기준으로 라운드로빈**하고, **최근 터치한
영역은 항상 보낸다.** 이게 두 가지를 동시에 해결한다.

- **대역폭 절벽이 수렴 지연으로 바뀐다.** 프레임당 N타일 고정이면 화면이 아무리
  크게 바뀌어도 송신량이 안 늘어난다. "한계에서 입력이 아니라 화면이 먼저
  희생된다"를 스케줄러가 구조적으로 보장한다.
- **아래 적은 "버린 타일이 영구히 썩는" 문제가 사라진다.** 라운드로빈이 결국
  모든 더티 타일을 방문하므로 **자가 치유**가 공짜로 나온다. 합집합 이월도
  주기적 전체 갱신도 필요 없어진다.

최근 터치 영역 우선은 주의(attention)에 맞춘 우선순위다 — 펜 끝은 풀 레이트로,
주변은 게으르게 수렴한다. 절대크기 타일은 영역이 커질 때 타일 **개수**가 늘게
해서 타일당 비용을 예측 가능하게 유지한다.

대가는 전면 변경 시 수렴 중에 옛 화면과 새 화면이 섞인 **패치워크**가 보이는
것이다(300타일에 8타일/프레임이면 30fps에서 1.2초). 더티 **나이순** 우선을
섞거나 move rect를 다루면 완화된다.

#### 포맷은 JPEG가 아니라 블록 압축

**BC3는 데스크톱 포맷이라 안드로이드에서 보장이 안 된다** (Adreno·Mali가
S3TC를 일반적으로 노출하지 않는다). 대응물은 **ETC2** — GLES 3.0 필수이고,
이 앱이 이미 요구하는 바로 그 버전이다. 알파가 필요 없으니 RGB 4bpp,
RGBA8 대비 **8:1 고정**이다.

이득은 압축률이 아니라 **파이프라인 전체가 사라지는 것**이다. 아래 "함정"에
적은 JPEG의 숨은 비용이 전부 없어진다.

- **GPU→CPU 리드백이 없다.** DXGI가 준 D3D11 텍스처를 **컴퓨트 셰이더로 그
  자리에서** 블록 압축하고, 내리는 것은 1/8 크기의 압축 데이터뿐이다. JPEG는
  원본을 매 프레임 내려야 했다.
- **게스트 디코딩이 0이다.** zstd 풀고 `glCompressedTexSubImage2D` 로 바로
  꽂는다. 디코더도 색공간 변환도 RGBA 스테이징도 없다 — 폰 발열에도 좋다.
- **부분 갱신이 자연스럽다.** 4x4 정렬만 지키면 타일이 그대로 텍스처 서브영역
  이다. 깍두기 구조와 1:1로 맞는다.
- **송신량이 정확히 예측된다.** 고정 크기라 "N타일 = 정확히 M바이트"다. JPEG의
  가변 출력으로는 하드 예산에 맞춘 스케줄링이 훨씬 까다롭다.
- 호스트 CPU도 안 쓴다. zstd 레벨 1~3은 수백 MB/s다.

zstd가 위에서 버는 양은 실측했다 (`test_tile_payload.cpp`, 256x256, level 1,
BGRA 원본 대비 최종 비율):

| 내용 | 비율 |
|---|---|
| 창 같은 것 (제목표시줄·툴바·글줄) | **333 : 1** |
| 랜덤 노이즈 (바닥) | **8.4 : 1** |
| 64x64 평면 타일 | **25 바이트** |

바닥이 8.4:1인 게 핵심이다. **랜덤 블록은 zstd가 손댈 게 없으므로** 고정
비율에서 거의 안 내려간다 — 그래서 "타일 N개 = 최대 몇 바이트"가 성립하고,
예산이 예산이 된다.

그리고 위쪽은 아주 후하다. 평평한 배경과 반복되는 글자 모양은 같은 블록의
반복이 되고, 그게 ETC2가 남긴 잉여를 zstd가 걷어가는 지점이다. **손대지 않은
영역이 25바이트**라는 건, 안 바뀐 곳이 사실상 공짜라는 뜻이다.

(창 쪽 숫자는 합성 이미지다. 실제 UI는 이보다 낮겠지만 바닥에서 한참 위인
것은 분명하다. 반대로 "사진 같은 내용"을 산술 패턴으로 흉내 내면 zstd가 그
주기성을 찾아내 57:1 같은 숫자가 나오는데, 그건 측정이 아니라 자기기만이라
난수로 바꿨다.)

**대가는 글자다** — 라고 예상했는데, 재보니 생각보다 낫다. 블록 압축은 4x4 안을
끝점 둘로 양자화하고 글자는 전부 경계라 걱정했지만, ETC1의 모델이 "베이스 색 +
픽셀별 휘도 오프셋"이라 **안티에일리어싱된 검은 글자/흰 배경은 순수한 휘도 변화**
이고 이건 이 모델이 잘하는 것이다.

실측 PSNR (`test_etc2.cpp`, 왕복):

| 내용 | PSNR |
|---|---|
| 순수 흰색·검은색 평면 | **무손실** |
| 중간 회색·유채색 평면 | 39.7 ~ 45.9 dB |
| 글자 (검정/흰색, AA 포함) | **34.1 dB** |
| 부드러운 그라디언트 | 37.8 dB |
| 랜덤 노이즈 (최악) | 13.4 dB |

순수 흰색·검은색이 무손실인 건 **클램핑 덕이다**: 베이스 255에 +2를 더해도
255에서 잘리고, 0에 -2를 더해도 0이다. 그리고 UI는 대부분 그 둘이다.

여전히 **품질 노브가 없다** — JPEG는 품질 95로 올릴 수 있지만 ETC2는 못 한다.
약한 지점도 그대로다: **한 4x4 안에 서로 다른 색상(hue) 두 개**, 즉 유채색
배경 위의 유채색 글자. 거기가 거슬리면 ASTC로 올린다.

여기서 라운드로빈이 답을 준다. 원래 대역폭 완충 장치는 "해상도 비율"이었는데
**글자한테는 축소가 어떤 코덱보다 치명적이다.** 라운드로빈은 대역폭을 해상도
대신 **시간으로** 지불하게 해준다 — 1:1 해상도를 유지하고 수렴만 느리게 하면
글자가 온전하다. 참고용 화면에서는 훨씬 나은 교환이다.

글자가 그래도 거슬리면 **ASTC 4x4** 로 한 단계 올린다. 같은 8bpp에 화질이
확실히 낫고 GLES 3.2 필수라 사실상 전 기기에 있다. 인코딩이 비싼 것이 문제인데
프레임당 타일 수가 이미 제한되어 있으므로 감당 범위다.

**사다리: ETC2+zstd → ASTC → 하드웨어 H.264.**

#### 함정들

**더티 타일은 상태가 있어서 프레임을 함부로 못 버린다.** H.264는 프레임을
버리면 화질이 잠깐 나빠지고 만다. 타일은 다르다 — N번 타일을 버리면 N+1번에는
그 변경이 없으니 **그 자리가 영구히 낡은 화면으로 남는다.** 그래서 버린
프레임의 더티 영역을 **다음 프레임에 합집합으로 이월**해야 하고, 어긋난 것을
낫게 할 **주기적 전체 갱신**이 보험으로 필요하다.

**TCP 헤드 오브 라인.** 우선순위 큐를 둬도 **커널 소켓에 넘긴 바이트는 이미
늦었다.** 200 KB 프레임을 한 번에 `send()` 하면 뒤따르는 POINTER는 200 KB
뒤다. 큐는 소켓 **위**에 있어야 하고 청크 사이에 입력을 확인해야 하며, 그러면
**청크 크기가 최악 입력 지연을 정한다** — 25 MB/s에서 16 KiB면 약 0.65 ms.
`PROTOCOL.md` 의 16 KiB 분할이 그래서 나온 숫자다.

**dirty가 안 도와주는 경우**: PC에서 동영상 재생(매 프레임 전면 변경),
스크롤과 캔버스 팬·줌. 그리고 아이러니하게도 **캔버스 자체가 사진 같은 내용**
이라 블록 압축이 제일 못하는 부분이다.

스크롤은 원래 **move rect** 로 싸게 처리할 생각이었는데, 재보니 **그게 안 온다**
(아래 실측 참조). 스크롤은 진짜로 창 전체 리페인트이고, 그걸 흡수하는 건
move rect가 아니라 **타일 예산**이다. 다행히 라운드로빈 설계는 애초에 move rect에
기대지 않는다.

**JPEG를 1단계에서 뺀 이유가 여기 있다.** CPU 인코딩이면 DXGI가 준 D3D11
텍스처를 내려야 하니 하드웨어 H.264가 피하는 그 리드백이 생기고, libjpeg-turbo
1080p 단일 스레드가 대략 5~15 ms/frame이라 30fps면 코어 하나를 거의 다 쓴다.
그 CPU는 입력 경로와 경쟁한다. 타일마다 따로 압축하면 MCU(16px) 경계에 정렬하고
품질을 고정해야 이음매가 안 보이고, 글자가 읽히게 품질을 올리는 만큼 대역폭
여유가 사라진다 — **품질 노브와 대역폭 노브가 같은 노브다.** 블록 압축은 이
네 가지를 전부 피한다.

**링크 밖.** 폰은 충전되면서 계속 디코딩하므로 발열·스로틀링이 있고, 그건
**터치 지연에도 영향을 준다.** USB도 전용이 아니라 같은 루트 허브에 다른 장치가
붙으면 예산이 준다.

#### 실측 (`--capture-test`, 1920x1080, 이 PC)

DXGI가 실제로 뭐라고 하는지는 남의 드라이버에 대한 주장이라 재봤다.
호스트를 `--capture-test` 로 띄우면 8초간 지켜보고 요약을 찍는다. 폰 필요 없다.

| 상황 | 프레임 | 간격 | 프레임당 dirty 면적 | dirty 사각형 | move |
|---|---|---|---|---|---|
| 대체로 유휴 | 478 | 16.7 ms | **3.3%** | 프레임당 ~1 | **0** |
| 텍스트 창 연속 스크롤 | 481 | 16.6 ms | **11.0%** | 프레임당 ~2.3 | **0** |
| 창 드래그 | 478 | 16.7 ms | 2.0% | 프레임당 ~1.1 | **0** |

**좋은 소식**: 디스플레이 주사율대로 60fps로 들어오고, 코얼레싱이 거의 0이라
캡처가 밀리지 않는다. 그리고 **프레임당 변경 면적이 정말로 작다** — 스크롤
중에도 11%다. 더티 기반 설계의 전제가 확인됐다.

**나쁜 소식**: **move rect가 한 번도 안 왔다.** 유휴·스크롤·창 드래그 셋 다 0이다.
DWM이 블리팅이 아니라 합성을 하므로 컴포지터 눈에는 "밀림"으로 보이는 게 없다.
`docs` 이전 판에 "스크롤은 move rect로 싸게 처리하면 된다"고 적었는데 **틀렸다.**

단서 하나: **양성 대조가 없다.** move rect를 한 번도 못 봤으니 "왔는데 내 파싱이
놓쳤을" 가능성을 배제하진 못한다. 다만 같은 버퍼·같은 패턴으로 읽는 dirty 쪽은
활동에 따라 정확히 반응하므로 파싱 자체는 동작한다.

**결론: move rect 처리를 우선순위에서 뺀다.** 인터페이스에는 남겨둔다 — X11과
PipeWire는 damage를 다르게 주고, 아무도 안 채우는 필드는 비용이 0이다.

#### 인코더가 맞다는 걸 어떻게 아는가

인코더와 디코더를 같이 짜서 왕복시키면 **서로 일치한다는 것만 증명된다.**
비트 레이아웃을 양쪽에서 똑같이 잘못 기억했으면 왕복은 완벽하고 GPU에서만
쓰레기가 나온다. 그리고 이 레이아웃은 기억에서 나온 것이다.

그래서 `--etc2-test` 로 **남이 짠 디코더**에 맞춰본다: 데스크톱 GL 드라이버다.
폰과 같은 명세를 구현하고 있으므로 대조군으로 유효하다. 프로브 이미지를
인코딩해 `GL_COMPRESSED_RGB8_ETC2` 로 올리고, `glGetTexImage` 로 되읽어
우리 디코더 결과와 비교한다.

원본이 아니라 **우리 디코더와** 비교하는 게 요점이다. 질문은 "인코더가 원본을
얼마나 잘 담았나"가 아니라 "이 비트들이 양쪽에 같은 뜻인가"이기 때문이다.

결과: NVIDIA 591.86 (GL 4.3)에서 **모든 픽셀이 정확히 일치**. 레이아웃이 맞다.

#### 우선순위 송신 큐

포인터 메시지 수십 바이트와 타일 묶음 수십 킬로바이트가 소켓 하나를 공유한다.
생산된 순서대로 내보내면 후자가 전자를 묻는다.

**큐가 소켓 아래에 있으면 아무 소용이 없다.** 커널 버퍼에 넘긴 바이트는 이미
확정이라, 프레임을 한 번의 `send()` 로 밀어넣으면 큐를 어떻게 정렬했든 모든
포인터가 그 뒤에 선다. 그래서 `SendQueue` 는 소켓 **위**에 있고 한 번에 메시지
하나씩만 내보낸다.

**못 하는 것**: 이미 나가고 있는 메시지는 못 끊는다 — 끊으면 스트림이 파싱되지
않는다. 그래서 인터랙티브 메시지가 겪을 수 있는 최악의 대기는 **큐 전체가 아니라
지금 나가는 메시지 하나의 잔량**이고, 프레임을 여기 오기 전에 잘라두는 이유가
그것이다. `inversion_bytes()` 가 그 값을 내주므로 주장이 아니라 확인이 된다.

전송에는 **스레드가 따로 붙는다.** 수신 루프는 평생 `recv()` 에 블록되어 있어서
큐를 비울 주체가 없고, 아무도 안 비우는 큐는 그냥 느린 소켓이다. 소켓 호출은
락을 놓고 하며(청크를 복사해서 나간다), 락을 쥔 채 블로킹 쓰기를 하면 이 구조가
지키려는 바로 그 포인터 경로가 멈춘다.

`send()` 의 반환값은 이제 **"보냈다"가 아니라 "넣었다"** 이다. 링크가 죽은 건
하트비트가 알려주고, 여기서 기다리는 것이 이 큐가 없애려는 것이다.

프레임은 **한 번에 하나만** 태운다(`bulk_idle()`). 그래야 밀릴 때 버리는 게
안전하다 — 스케줄러는 실제로 나간 타일만 clean으로 표시하므로, 안 나간 것은
그냥 다음 바퀴에 다시 온다.

**실측**: 송신 경로를 전부 갈아끼운 뒤 S23 울트라에서 이벤트-투-호스트
**11.3 ms 평균 / 20.1 ms 최대**, RTT 3.02 ms. 1차 마일스톤 기준선과 같다.

#### 호스트 송신 경로 (구현됨)

`VIEWPORT_REQ` 수신 → 캡처 → 더티를 타일로 → 스케줄러가 예산만큼 선택 →
타일별로 잘라내고(필요하면 축소) ETC2 → zstd → `FRAME_INFO` + 16 KiB
`FRAME_DATA` 를 Bulk 우선순위로.

좌표계가 셋(데스크톱 / 인코딩 표면 / 타일)이라 변환을 `ViewportGeometry` 로
따로 뺐다. 여기서 1픽셀 어긋나면 화면 한 조각이 미묘하게 엉뚱한 자리에
찍히는데, 폰에서 눈으로 찾는 것보다 테스트로 잡는 게 훨씬 싸다. 소스 사각형은
원점+크기가 아니라 **모서리 기준**으로 매핑한다 — 그래야 이웃 타일이 정확히
맞물리고 데스크톱 열 하나가 둘 사이로 사라지지 않는다.

축소는 **최근접이 아니라 면적 평균**이다. 글자를 최근접으로 줄이면 획이 통째로
빠지고, 글자가 이 기능의 주 용도다.

**`--frame-test`** 가 폰 없이 전 구간을 돌린다. 부품마다 테스트가 있다는 것과
부품이 맞물린다는 것은 다른 얘기라서, 배치를 **다시 이미지로 복원해서** 파일로
쓴다. 타일이 엉뚱한 자리에 붙는 종류의 오류는 눈으로만 잡힌다. 이 복원 코드가
곧 게스트 수신부의 참조 구현이기도 하다.

실측 (1920x1080 → 960x540, 64px 타일 135개, 20fps, 6초, Debug 빌드):

```
49 batch(es), 652 tile(s), 434.5 KiB sent from 1185.9 KiB of blocks (2.7x)
652 tile(s) reassembled across 49 batch(es); 0 malformed, 0 stray seq
last encode 19.8 ms
```

복원된 이미지는 데스크톱 그대로였다 — 타일 배치 정확, 이음매 없음, 반각 축소인데
한글도 읽힌다.

여기서 **실제 버그를 하나 잡았다.** 처음엔 `next()` 를 큐가 빌 때까지 돌려
더티를 모았는데, `next()` 는 새로 얻기 전에 **들고 있던 프레임을 놓는다**
(DXGI가 그걸 요구한다). 그래서 루프가 끝난 시점엔 읽을 프레임이 없었다 —
캡처 346회에 배치 0개. 틱당 한 번만 얻고 그 프레임을 잡은 채로 읽는다.
놓치는 건 없다: 틱이 배치보다 훨씬 잦고, 그 사이에 일어난 일은 드라이버가
합쳐서 `AccumulatedFrames` 로 알려준다.

#### 게스트 수신 (구현됨)

`FRAME_INFO` 가 배치를 열고 `FRAME_DATA` 가 `offset` 으로 채운다. 다 차면 zstd를
풀고, 타일 인덱스 목록을 걸으며 `glCompressedTexSubImage2D` 로
`GL_COMPRESSED_RGB8_ETC2` 텍스처에 **그대로** 넣는다. 이쪽에 디코더는 없다 —
그게 이 포맷을 고른 이유고, GPU가 샘플링하면서 공짜로 푼다.

**타일 산술은 공유한다.** `ViewportGeometry` 와 `etc2_size` 를 `common/` 으로
옮겼다 (`digitiz/proto/tiling.hpp`). 게스트는 타일 번호를 사각형으로 되돌리고
타일 바이트 수만큼 페이로드를 걸어야 하는데, 이건 호스트가 채울 때 쓴 것과 **같은
산술이다.** 사본이 둘이면 조용히 어긋난다: 1픽셀 차이는 그림이 밀리고, 1바이트
차이는 그 뒤 모든 타일이 엉뚱한 자리에 간다. 둘 다 에러를 내지 않는다.

**요청은 뷰가 멈춘 뒤에 보낸다.** 지금 보고 있는 PC 영역을 `ViewTransform` 에서
뽑아(`to_pc` 로 서피스 두 모서리) 데스크톱에 클립해서 보낸다. 핀치·팬 중에 매
프레임 보내면 호스트가 그때마다 타일 번호를 다시 매기고 전부 미전송으로 돌리므로
전송이 영원히 다시 시작되고 한 번도 안 끝난다. 250 ms 정착 대기 — 활성 창 200 ms
와 같은 이유, 같은 처방. 영역은 32 PC px, 인코딩 크기는 64 px 격자에 스냅한다.
후자가 더 단단한 이유는 인코딩 크기가 바뀌면 텍스처까지 버리기 때문이다.

**그리드 위에 그린다** (계획은 아래였는데 바꿨다). 그리드는 배경이고, 그림이 있는
자리에서는 그림이 "여기가 PC다"라는 말이다. 그림이 닿지 않는 바깥에서 그리드가
계속 그 말을 한다. 화면이 켜져 있으면 미니맵은 숨는다 — 미니맵은 "지금 PC의 어디를
보고 있나"에 답하려고 있는데 그림이 더 잘 답한다.

측정 (S23 Ultra, 1920x1080 → 1152x640, 30 fps, 양쪽 각각 스트로크 5회):

```
스트림 끔    14.0 ms avg, 23.8 max
스트림 켬    13.5 ms avg, 18.8 max
```

**입력 지연 비용이 측정되지 않는다.** 노이즈 안이다. 16 KiB 청크와 우선순위 큐가
하려던 일이 이것이었다.

여기서도 **실제 버그를 하나 잡았다.** 앱을 백그라운드로 보내면 게스트는 듣기만
멈추고 호스트에게 말하지 않았다. 호스트는 아무도 비우지 않는 큐에 계속 인코딩해
넣었고, 돌아올 때 배치 2개가 버려진 것으로 드러났다. 이제 멈춘다고 말한다.
큐 상한(8배치)은 그래도 남겨뒀다 — 렌더 스레드가 없는 동안 네트워크 스레드는
계속 돌기 때문이다.

#### 한 번에 보내는 단위 — 스위프 N개 + 펜 1개

예산을 바이트로 잡은 것이 잘못이었다. `budget_bytes_ = 384 KiB` 는 **192타일**인데
1152×640 격자가 **180타일**이다. **예산이 격자보다 커서 한 번도 걸리지 않았다.**
스위프가 매번 전체를 한 바퀴 돌고 끝나니 수렴이라는 개념 자체가 없었고, 갱신은
항상 368 KiB 한 덩어리였다. 이 문서가 스스로 적어둔 문장이 이것이다:

> **"타일 N개 = 최대 몇 바이트"가 성립하고, 예산이 예산이 된다**

`TileScheduler.hpp` 주석에도 "the frame budget is a **fixed number of tiles**" 라고
써놓고 구현은 바이트로 했다.

**확정된 단위:**

```
전송 1회 = 스위프 N개 + 펜 타일 1개
```

- **펜 타일은 N에 포함되지 않는다.** 예산 안에서 앞자리를 주면 펜이 스위프의 몫을
  뺏어서, 화면이 크게 바뀔 때 둘이 서로를 갉아먹는다. 밖으로 빼면 독립한다 —
  스위프는 N의 속도로 꾸준히 수렴하고 펜 자리는 매 회차 갱신된다.
- **접촉 중에만.** 펜을 떼면 그 회차부터 스위프만.
- **더티 여부와 무관하게 보낸다.** 그래야 자기 획이 손가락 밑에서 바로 보인다.
- **N은 호스트 설정, 기본 1.** 폰이 정하지 않는다. 게스트는 "어느 영역을 어떤
  해상도로"만 말하고, "한 번에 얼마나"는 호스트, 실제 속도는 링크가 정한다.

**N은 속도가 아니라 한 번에 넣는 양이다.** 속도는 `fps` 가 정하고, 큐가 안 비었으면
그 회차를 거르는 것이 백프레셔다. 그래서 스위프 수렴은 `fps × N` 타일/초, 펜 타일은
`fps` 로 갱신된다(N과 무관). 크기는 한 번에 정확히 `(N+1) × 2048` 바이트로 내용과
무관하게 예측 가능하다 — 절대크기 타일을 고른 이유가 그것이다.

~~N=1은 펜 신선도에 예산을 몰아준 값이다~~ — **틀렸다.** 펜 타일은 예산 **밖**이라
N이 얼마든 매 배치에 나간다. 펜 갱신율은 `fps` 지 N의 함수가 아니다. N이 정하는
것은 스위프 속도뿐이다. 아래 측정을 보면 N=1은 그냥 손해다.

**앞선 기록 두 개를 물린다.**

- *"배치를 잘게 쪼개면 오히려 나빠진다 (6배치 = 6틱 = 200 ms)"* — N=192를 전제로 한
  순환논증이었다. 원인(예산이 안 걸림)을 증상(게이트가 병목처럼 보임)으로 착각했다.
- *"`ZSTD_decompressStream` 으로 게스트가 점진적으로 그리게 하자"* — 필요 없다.
  작은 배치는 그 자체로 점진적이다. 배치가 압축 단위로 남아야 타일 사이 중복에서
  나오는 2.7×가 유지된다.
- *"전체화면 채우는 데 6초"* — **최악의 경우를 대표값처럼 적었다.** 전체가 항상
  더티라는 가정인데다, 펜으로 쓰려면 확대해서 쓰므로 격자가 훨씬 작다. 400×300 PC
  영역이면 `out` 384×320, 격자 6×5 = **30타일**이고 전체 리페인트도 1초다. 그마저
  뷰를 바꿀 때뿐이고 평상시엔 몇 타일만 더티다. 축소해서 전체를 보는 건 "지금 어디가
  뭐지"를 확인하는 상태지 그리는 상태가 아니다.

**남은 작업** (전부 호스트만 건드린다 — 게스트 빌드·실기 확인이 필요 없어 반복이 싸다):

1. ~~예산을 절대 타일 수로~~ ✅
2. 펜 타일을 예산 밖으로. `set_focus()` 를 아무도 안 부르니 관측 가능한 동작은
   안 바뀐다 — 안전하게 먼저 넣을 수 있다
3. `set_focus()` 배선. 호스트가 `Pointer` 를 받을 때 PC 좌표 → `tiles_touching()`
   → 타일 1개. Down/Move에서 설정, Up/Cancel에서 해제. 여기서 처음 눈에 보인다
4. 호스트 config 파일. N을 저장할 곳이 없다 (설정 파일이 게스트에만 있다)
5. 권장 N 실시간 계산 (후순위). 큐 드레인 속도가 곧 대역폭 측정값이라, 목표 수렴
   시간을 주면 N을 역산할 수 있다

#### 굶어 죽던 타일 (고침, 실기 확인됨)

리드백이 fps 시계에 묶여 있었는데 **픽셀은 프레임을 쥐고 있는 동안에만 읽을 수
있고, 멈춘 화면은 더 이상 프레임을 주지 않는다.** 그래서 예산이 한 틱에 못 끝낸
변화는 나머지 타일이 더티로 남고, 그 뒤 화면이 멈추면 그것을 읽어낼 프레임이
영영 오지 않았다. 다른 무언가가 화면을 움직일 때까지 틀린 채로 남는다 —
스위프가 보장한다던 "어떤 타일도 굶지 않는다"가 무효였다.

리드백을 **프레임 도착 + 버퍼가 아직 담지 못한 더티**에 붙이고, fps는 전송에만
남겼다. 버퍼가 마킹된 것을 전부 담은 뒤라면 "새 프레임 없음" 은 "읽은 뒤로 화면이
안 움직였음" 이므로 그 버퍼에서 보내는 것이 곧 현재 픽셀을 보내는 것이다.

펜 타일만 밀린 경우에도 배치가 나가게 했다. 정적 화면 체크가 앞에 있어서
"더티와 무관하게 보낸다" 가 한 번도 성립하지 않고 있었다.

(개발 중에는 앞 창이 초 단위로 카운터를 갱신해서 정적 화면을 만들 수가 없었다.
사용자가 원래 걸리던 조건에서 직접 해소를 확인했다.)

#### 검토하고 버림: 직전 프레임과의 diff 압축

zstd가 지금 먹는 것은 한 배치 안의 공간적 중복뿐이니, 시간적 중복 — 대부분의
타일이 직전과 거의 같다는 사실 — 도 먹이자는 안이었다. 양쪽이 직전 프레임을
따로 보관하고 diff를 압축해 보낸다. 호스트 쪽 보관본은 DXGI가 주는 무손실 8888이
자연스럽다.

**게스트에서 깨진다.** 게스트가 들고 있는 것은 ETC 블록인데, **압축 포맷은 GLES에서
프레임버퍼도 이미지 스토어 대상도 될 수 없다.** 픽셀 델타를 GPU에서 적용할 방법이
없다. CPU로 내려서 디코딩 → 적용 → 재인코딩을 해야 하는데, 그게 바로 ETC를 고른
이유였던 작업이다 (GPU가 샘플링하면서 푸는 것 말고는 아무도 디코딩하지 않는다).

**블록 도메인으로 바꿔도 안 된다.** 직전에 보낸 ETC 블록과 XOR해서 보내면 게스트는
CPU에서 XOR 한 번으로 끝나지만, ETC 블록 바이트는 픽셀이 조금만 달라져도 크게
흔들린다 (베이스 색 양자화와 픽셀별 modifier 인덱스). 그래서 XOR이 0에 가까운
경우는 **비트까지 동일한 블록**뿐인데, 그런 타일은 애초에 안 보낸다. 실제로 보내는
타일에 대해서는 이득이 거의 없다.

버린다.

#### 구간별 실측 — 병목은 리드백이다

`--frame-test`, Release, 1920x1080 → 960x540, N=1, 6초:

| 구간 | 시간 | 어떻게 붙나 |
|---|---|---|
| **리드백** | **3050 us** | **배치당 (N과 무관)** |
| ETC2 | 659 us | 타일당 |
| 면적평균 축소 | 182 us | 타일당 |
| **zstd** | **27 us** | 배치당 |

배치 하나 = **3.05 ms + 0.84 ms × N**.

**zstd는 배치 비용의 0.7%다.** 빼서 아끼는 게 27 us고 대가는 2.7배 대역폭이다.
**뺄 이유가 없다** — 이 질문은 닫는다.

**그리고 N=1은 최악의 값이다.** 리드백 3 ms를 치르고 2 KB짜리 타일 하나를 보낸다.
고정비가 배치당이라 N을 키우면 타일당 비용이 급격히 떨어진다:

| N | 배치 시간 | 타일당 |
|---|---|---|
| 1 | 3.9 ms | 3.9 ms |
| 8 | 9.8 ms | 1.2 ms |
| 16 | 16.5 ms | 1.0 ms |
| 32 | 30.0 ms | 0.9 ms |

호스트 루프가 33 ms(30 Hz)니 N=16이 그 절반, N=32가 거의 전부다. **실용 상한은
16 근처**고, N=1을 기본으로 둔 것은 근거가 없어졌다.

**리드백이 왜 그렇게 비쌌나.** 타일 하나를 쓰든 백 개를 쓰든 **영역 전체**를
GPU에서 CPU로 내리고 있었다 (960x540 BGRA = 2 MB). 고쳤다 — 아래.

#### 고름: 고를 것을 먼저 고르고 그만큼만 읽는다

두 가지가 같이 필요했다.

**1. 캡처가 자기 GPU 사본을 갖는다.** 획득한 프레임은 **쥐고 있는 동안만** 읽을 수
있고 멈춘 화면은 다음 프레임을 주지 않는다. 그래서 부분 리드백을 그냥 넣으면
굶주림이 되돌아온다 — 버퍼가 직전 선택분만 덮는데 다음 선택은 거기 없고, 읽을
프레임도 없다. 획득할 때마다 `CopyResource` 로 우리 텍스처에 복사하고 거기서
읽으면 그 결합이 통째로 사라진다.

부수 효과로 **"영역이 바뀐 직후 화면이 얼어 있으면 첫 리드백이 영영 안 되는"**
잔여 구멍도 닫혔다. `pixels_stale_` / `region_valid_` 같은 신선도 추적도 필요
없어졌다 — 인코딩 직전에 필요한 만큼 읽으면 되니 낡을 틈이 없다.

**2. `select()` 를 리드백 앞으로.** 선택된 타일들의 바운딩 박스만 읽는다. 이건
compute 인코더가 어차피 요구하는 순서이기도 하다 — 어느 타일인지 모르면 디스패치를
못 한다.

측정 (같은 조건, N=1):

| 구간 | 전 | 후 |
|---|---|---|
| **리드백** | 3050 us | **478 us** |
| ETC2 | 659 us | 564 us |
| 축소 | 182 us | 180 us |
| zstd | 27 us | 26 us |

배치 하나 = **0.5 ms + 0.74 ms x N**. 복원 이미지는 그대로 정확했다 (0 malformed,
폰에서도 창 경계가 어긋나지 않는다). 실사용에서도 확인 — 영상 재생 중인 데스크톱에서
리드백 859 us, 압축 6.6:1.

**남은 고정비가 다음 질문의 답이다.** 64x64 타일 하나가 데스크톱에서 128x128,
64 KB인데 읽는 데 478 us다. 대역폭은 (3050-478) us에 2 MB이므로 약 800 MB/s이고,
그 계산이면 64 KB는 80 us다. **나머지 400 us는 map/동기화 고정비다.**

그래서 compute 인코더가 가져갈 몫은 이렇다: 타일당 0.74 ms의 CPU 작업이 GPU로
넘어가고, 리드백은 블록만 내리므로 대역폭 항이 사라진다. 그래도 **고정비 400 us는
남는다** — 디스패치 결과를 map 하는 한. N=1 기준으로는 1.2 ms가 0.5 ms 정도,
N=16 기준으로는 12 ms가 0.5 ms 정도가 된다. 큰 N일수록 이득이 크다.

(N을 키우면 바운딩 박스도 커지므로 위 478 us는 N=1 값이다. 다만 영역 전체보다는
항상 작다.)

#### GPU에서 인코딩한다 (구현됨)

픽셀이 버스를 건너 CPU에서 인코딩되던 것을, 픽셀이 이미 있는 곳에서 인코딩하고
**블록만** 건너오게 바꿨다. 픽셀당 4바이트가 0.5바이트가 되고, 타일당 CPU 작업이
통째로 사라진다.

셰이더는 `Etc2.cpp` 와 **같은 인코더**다 — 같은 후보를 같은 순서로, 같은 면적평균,
같은 비트 배치. HLSL에 64비트 정수가 없어서 블록을 상위/하위 워드로 들고 다니다가
나갈 때 바이트 스왑한다 (패킹이 MSB 우선).

`--gpu-encode-test` 가 DXGI도 폰도 없이 자기 D3D11 디바이스를 만들어 대조한다.
기준은 "동점이 반대로 깨질 수 있으니 PSNR만 같으면 통과" 였는데 **네 이미지 전부
바이트까지 같게** 나왔다.

폴백이 남아 있다. `IFrameSource::encode_tiles()` 는 기본이 `false` 라 셰이더가 없는
플랫폼은 그대로 픽셀을 읽어 CPU에서 인코딩한다. 타일이 출력 경계 밖으로 걸치면
Windows 백엔드도 `false` 를 돌려준다 — 셰이더는 밖을 0으로 읽고 CPU는 건너뛰어서
결과가 달라지기 때문이다.

측정 (`--frame-test`, N=4, 1920x1080 → 960x540):

| 구간 | CPU 경로 | GPU 경로 |
|---|---|---|
| 타일당 축소 | 153 us | **0** |
| 타일당 ETC2 | 512 us | **0** |
| 배치당 리드백/맵 | 730 us | 1112 us |
| 배치 합계 | 약 3.4 ms | **약 1.8 ms** |

80배치 전부 GPU, 0 malformed, 폰에서 그림 정확.

**맵 대기가 오히려 늘었다.** 디스패치가 실제 GPU 작업을 얹으니 그만큼 더 기다린다.
그래도 타일당 CPU 2.7 ms가 사라져서 순이득이다.

**그리고 N이 커질수록 격차가 벌어진다.** 사용자가 N=128에서 배치당 2651 us를 쟀다.
N=4의 1112 us에서 N을 32배로 올렸는데 시간은 2.4배다 — 타일당으로는 278 us에서
**20.7 us**. 같은 조건의 CPU 경로는 타일당 665 us라 N=128이면 배치 하나에 85 ms,
33 ms 틱을 한참 넘긴다. 고정비가 지배하고 타일당 비용이 거의 0이라는 뜻이고,
예산을 크게 잡는 것이 이제 싸다.

**비동기 리드백은 하지 않기로 했다.** 남은 맵 대기는 배치당 약 1.1 ms고, 33 ms
틱의 3%다. 그걸 없애자고 배치 한 번분(33 ms) 화면 지연을 무는 것은 손해다 —
compute 전에는 리드백이 3 ms에 타일당 CPU까지 붙어 있어서 얘기가 달랐다.
숫자가 바뀌면 결론도 바뀐다.

#### 기본 예산을 32로

비용이 거의 전부 고정비가 됐으므로 예산을 크게 잡는 것이 싸다.

| N | 배치당 | 180타일 전체 수렴 |
|---|---|---|
| 4 | 1.15 ms | 1.5 초 |
| **32** | **1.72 ms** | **0.2 초** |
| 128 | 2.65 ms | 0.05 초 |

0.57 ms 더 쓰고 수렴이 7배 빨라진다. 더 올리지 않는 이유는 호스트 시간이 아니라
**링크**고, 그건 이미 큐가 강제한다 (직전 배치가 다 빠지기 전에는 새로 만들지
않는다).

스트로크 지연은 그대로다 (`sweep_tiles=29`, 스트림 켬, 스트로크 5회):

```
event-to-host 14.1 ms avg
```

오늘 잰 다른 값들과 같다 — 스트림 끔 14.0, N=1 13.5, N=29 14.1. **평균은 노이즈
안이다.** 최대값은 비교할 수 없다: 눌림 지연(핀치 수정)이 스트로크 첫 샘플에
얹히는데 아침 측정에는 그게 없었다.

#### 인코딩 비용이 N을 정한다

전송 1회가 스위프 N개 + 펜 1개인데, 그 N을 정하는 것은 대역폭이 아니라 **인코딩
시간**이다. 링크는 놀고 있고 UI 스레드는 안 그렇다.

`--frame-test`, 1920x1080 → 960x540, 타일당:

| 빌드 | 타일당 인코딩 |
|---|---|
| Debug | 약 4 ms |
| **Release** | **0.7 ms** |

타이머가 재는 구간은 zstd만이 아니라 **면적평균 축소 + ETC2 + zstd + 직렬화**
전체다. 리드백만 빠져 있다.

**그래서 빌드를 릴리스로 옮겼다.** 여기까지 Debug로 재고 있었는데, 그건 인코딩이
기능 한계를 정하는 프로그램에서 그 한계를 다섯 배 낮게 보고 있었다는 뜻이다.
0.7 ms면 33 ms 예산에서 N=16이 11 ms, N=32가 22 ms다. Debug 수치로는 N=8도
빠듯해 보였다.

zstd를 뺄지는 이 값을 구간별로 쪼개 본 뒤에 정한다. 지금 아는 것은 합계뿐이고,
같은 조건에서 압축률은 3.6:1이었다.

**알고 두는 것 하나.** [`ImGuiShell.cpp`](../host/src/ui/ImGuiShell.cpp) 의
`kIdleTimeoutSec = 1.0/30.0` 때문에 호스트 창을 안 건드리면 루프가 정확히 30 Hz다.
그래서 `fps` 를 30보다 크게 요청해도 조용히 30에 걸린다. UI 유휴 주기가 전송 주기를
정하고 있는 셈인데, 지금 두 30이 우연히 같아서 드러나지 않는다.

#### 미해결로 남는 것 셋

- **정지한 화면에서는 새 영역이 안 온다.** [FrameSender.cpp](../host/src/screen/FrameSender.cpp)
  의 `if (!holding) return;` — 영역이 바뀌면 전 타일이 더티가 되지만 호스트는
  DXGI가 새 프레임을 줄 때까지 아무것도 못 보낸다. 획득한 프레임에서 직접 읽고
  매 틱 놓기 때문에 자기 사본이 없다. **재현하지 못했다** — 개발 중에는 이 PC
  화면이 계속 바뀌어서 정지 상태를 만들 수 없었다. 고치려면 획득할 때마다 우리
  텍스처로 한 번 복사해 `read()` 가 새 프레임 없이도 서빙하게 한다.
- **슬라이딩 모드와 충돌한다.** 화면 전송은 영역이 절대 좌표로 고정되어야 성립하는데
  슬라이딩은 축척만 남기고 위치를 버린다. 지금은 슬라이딩일 때 화면·미니맵을 둘 다
  끈다. 더 나은 답이 있으면 그때.
- **호스트가 주 출력만 캡처한다** (`EnumOutputs(0)`). 요청 영역이 다른 모니터에
  걸치면 그쪽은 안 온다. `IFrameSource::bounds()` 가 이미 그 사실을 노출하므로
  인터페이스를 바꾸지 않고 고칠 수 있다.

작은 것 하나 더: 인코딩 크기가 바뀌면 텍스처를 다시 만들고, 아직 안 온 타일 자리는
0으로 채운 ETC2 블록(거의 검정)이 보인다. 줌을 크게 바꿀 때 한 배치 동안 어둡게
채워지는 게 보인다. 스냅 덕에 자주 일어나진 않는다.

#### 코드 모양

이미 있는 플랫폼 인터페이스 패턴 그대로다.

```
IFrameSource   ← DxgiFrameSource / XDamageFrameSource / PipeWireFrameSource
IFrameEncoder  ← MfEncoder / VaapiEncoder      (또는 FFmpeg 하나로)
```

`IFrameSource` 가 "더티 사각형 + move 사각형 + GPU 핸들"을 내놓게 잡아두면
1단계와 H.264 단계가 같은 인터페이스를 쓴다. 1단계 작업이 버려지지 않는다.

`read()` 는 GPU→CPU 리드백이라 **본 파이프라인이 피하려는 바로 그 경로**다.
폰 없이 캡처를 눈으로 확인하고 소프트웨어 인코더에 먹일 것을 주려고 둔 것이지,
실제 전송 경로가 아니다.

### M2의 지배적 제약

USB 2.0 실효 대역폭은 **20~35 MB/s** 수준이다 (전송 계층과 무관하게 USB가 상한).
1080p BGRA 30fps = 250 MB/s로 **한 자릿수 배 초과**.
따라서 화면 전송은 압축이 선택이 아니라 필수이며, 해상도 비율 옵션이
사용자가 조절할 수 있는 유일한 완충 장치다.

흐름 제어에서 **입력 지연은 화면 지연보다 항상 우선한다.**
프레임이 큐를 막아 포인터 이벤트가 밀리면 디지타이저로서 실격이다.

## 착수 전 확정 사항

전부 확정되었다. 상세는 [ARCHITECTURE.md §11](ARCHITECTURE.md#11-확정된-빌드-결정).

- C++20 / third_party는 **FetchContent** / 테스트는 **doctest**
- minSdk **24**, compileSdk 35, NDK **r27(LTS)** — `ndkVersion` 명시
- adb는 M1에서 **시스템 adb 요구** (번들은 배포 시점에 결정)

**유일한 선행 조건**: NDK r27 설치 (SDK Manager → SDK Tools → `Show Package Details`).
